# ADR-0002: версионированная передача состояния загрузки

Дата: 12.11.2026. Статус: контракт загрузочного прототипа v1, не стабильный продуктовый ABI. Источник определения — `include/styleos/boot_info.h`.

## Контекст и решение

UEFI x86-64 и QEMU `virt` AArch64 передают разные исходные сведения. Общему C-ядру нужен небольшой явно проверяемый контракт, который не предоставляет ему возможность случайно вызвать уже недействующие сервисы firmware.

`struct boot_info` имеет **96 байт**, выравнивание 8 и целочисленные поля фиксированной ширины. `magic = 0x5354594c454f5342`, `version = 1`, `size = 96`. В контракте нет C-указателей, callback firmware, map key UEFI или неявного владения памятью. Поля с адресами задаются как физические `uint64_t`; текущий стартовый код обязан обеспечить доступ к ним в своей модели адресации.

| Смещение | Поле | Тип и смысл |
|---|---|---|
| 0 | `magic` | u64, идентификатор StyleOS boot handoff |
| 8 | `version` | u32, версия раскладки |
| 12 | `size` | u32, размер структуры |
| 16 | `arch` | u32: 1 = x86-64, 2 = AArch64 |
| 20 | `platform` | u32: 1 = UEFI, 2 = QEMU `virt` |
| 24 | `flags` | u64: bit 0 = Boot Services завершены, bit 1 = DTB присутствует |
| 32 | `memory_map` | u64, физический адрес сырого массива дескрипторов UEFI |
| 40 | `memory_map_size` | u64, длина массива в байтах |
| 48 | `descriptor_size` | u32, шаг дескриптора UEFI, полученный от firmware |
| 52 | `descriptor_version` | u32, версия дескриптора UEFI |
| 56 | `dtb` | u64, физический адрес DTB при AArch64 boot |
| 64 | `uart_base` | u64, архитектурное расположение раннего UART |
| 72 | `boot_el` | u32, EL при входе общего ядра; для AArch64 прототипа = 1 |
| 76 | `reserved0` | u32, ноль |
| 80 | `reserved[2]` | 2×u64, нули |

Статические проверки размеров и ключевых смещений находятся рядом с объявлением. Динамическая проверка должна отклонять некорректные magic/version/size, неподходящие архитектуру и платформу, несовместимые флаги и поля памяти, EL и ненулевой резерв. Неверная структура не является основанием продолжать загрузку с молчаливыми значениями по умолчанию.

## x86-64 / UEFI

Загрузочный адаптер получает `GetMemoryMap` с точным `MapKey` и вызывает `ExitBootServices`. Между последним получением карты и попыткой выхода нельзя выполнять действия, способные изменить карту. Устаревший ключ требует обновления карты и ограниченного числа повторов; ошибку firmware или исчерпание лимита нужно явно диагностировать и завершить загрузку.

После успешного `ExitBootServices` нельзя обращаться к UEFI console, allocation services или другим Boot Services. Диагностика ядра идёт через собственный COM1. Переход на отдельный стек соблюдает x86-64 ABI используемой сборки, включая выравнивание и shadow space для Microsoft x64 calling convention.

Сохраняется **сырая** карта UEFI с её длиной, шагом и версией дескриптора. Её нельзя безусловно индексировать как компактный массив локальной C-структуры: фактический `descriptor_size` задаёт firmware. Успешное сохранение карты не означает наличие аллокатора или определения свободных страниц.

## AArch64 / QEMU virt

Стартовый код сохраняет входной `x0` с физическим адресом DTB до использования регистров. Поддерживаются определённые прототипом EL1/EL2 пути: при входе EL2 выполняется контролируемый переход к EL1, готовятся стек и C-окружение. Неподдерживаемый EL не выдаётся за успешную загрузку.

Флаг DTB и поле `dtb` передают местоположение boot metadata. Хранение адреса DTB не равнозначно разбору дерева, перечислению всей памяти или поддержке произвольных ARM-плат. PL011 QEMU `virt` пока задаётся платформенным адаптером; автоматического обнаружения драйверов нет.

## Память и время жизни

Образ, стек, `boot_info`, буфер карты UEFI и DTB должны оставаться доступны и зарезервированы до того, как будущий менеджер памяти явно примет их. Сам факт завершения Boot Services не разрешает немедленно перезаписать код или буфер, с которого ядро ещё читает.

T-P1.0 не реализует передачу владения страницами и не обещает защиту от злонамеренного адреса. Числовые проверки handoff выявляют описанные ошибки контракта, но не доказывают корректность любого физического указателя.

## Изменения контракта

Изменение раскладки или смысла полей требует новой версии, обновления обоих адаптеров, host/target-тестов и решения владельца. Продуктовые boot protocol, API и ABI будущей StyleOS не считаются утверждёнными этим документом.
