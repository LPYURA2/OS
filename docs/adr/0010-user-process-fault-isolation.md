# ADR-0010 — ограниченное сдерживание сбоя пользовательской программы

Дата: 16.11.2026. Статус: решение отдельного экспериментального профиля T-P1.7
в `feature/styleos-t-p1-7`, база
`eb73fad3ed431e91ebe995be4b370c678210e2b8`. Фактические результаты, проверенный
SHA и аппаратные журналы находятся в [отчёте](../test-results/t-p1-7/README.md).
Этот ADR не выбирает микроядерную, гибридную или монолитную модель StyleOS.

## Причина и разрешённая граница

T-P1.6 сохранил SP, PC и nonvolatile integer registers двух доверенных функций
ядра. Обе имели одинаковые привилегии и могли испортить память диспетчера.
Следующий проверяемый шаг — аппаратно выполнить две ограниченные программы
в CPL3/EL0, завершить только первую после известного memory fault и продолжить
вторую после него. Возврат к аварийной инструкции и исправление программы не
предусмотрены.

Только `--test-user-processes` включает новый путь. Он несовместим со всеми
девятью прежними флагами и имеет отдельный выход `build/user-processes` либо
явно выбранный отдельный каталог. После валидного handoff и MEMMAP допускаются
свои таблицы, пользовательские страницы, привилегированный стек входа и
необходимые x86 GDT/TSS/IDT либо ARM vectors/MMU. Это узкое разрешение нового
профиля; исторические [ADR-0005](0005-early-exception-diagnostics.md),
[ADR-0007](0007-owned-translation-tables-experiment.md),
[ADR-0008](0008-physical-memory-ownership-plan.md) и
[ADR-0009](0009-cooperative-kernel-tasks.md) сохраняют смысл для своих профилей.
Обычная загрузка, `boot_info v1`, нормализация и прежние образы не меняются.

Один CPU и явные аппаратные переходы определяют весь сценарий. Нет таймера,
IRQ, вытеснения, SMP, общего планировщика, загрузчика приложений, файловой
системы, IPC или стабильного syscall ABI. Программы встроены в образ; ядро
разрешает только тестовые уступку и штатный выход.

## Конечная память образа

Общие постоянные объекты имеют известные размеры:

| Объект | Размер | Срок жизни |
|---|---|---|
| `styleos_user_tables` | 3 × 32 × 4096 = 393216 байт | SAFE, A и B roots; таблицы остаются в резерве образа |
| `styleos_user_control` | 16384 байта | Дескрипторы, контексты, доказательства и отдельный arch scratch |
| `styleos_user_entry_stack` | 16384 байта | Привилегированный стек аппаратного входа из CPL3/EL0 |
| `styleos_user_stack_a`, `styleos_user_stack_b` | По 4096 байт | Отдельные пользовательские стеки |
| `styleos_user_data_a`, `styleos_user_data_b` | По 4096 байт | Отдельные writable данные |
| `styleos_user_code_a`, `styleos_user_code_b` | По 4096 байт | Встроенные машинные программы на отдельных страницах |

BSS-объекты выровнены на 4096. Последние 4096 байт control, начиная с offset
12288, зарезервированы для непрозрачного архитектурного scratch; общий
`struct up_demo` не пересекает его. x86 дополнительно содержит три отдельных
4096-байтных объекта GDT/TSS/IDT, которые также требуют полного допуска;
дополнительного отдельного arch control нет.
На ARM отдельно учитываются новые EL1 vectors размером 2048 байт с таким же
выравниванием; старые vectors остаются частью живого образа.

До первой записи нового эксперимента доказываются оба конца каждого диапазона,
арифметика, выравнивание, полный RESERVED/image extent и отсутствие пересечений
с существующим стеком, handoff, источником UEFI map/DTB, diagnostic workspace,
boot pool/metadata, векторами и прочими живыми объектами. Первоначальная
очистка BSS загрузчиком остаётся подготовкой C-среды. Бинарная проверка должна
покрывать полный PE/zero-fill/runtime extent либо ELF/PT_LOAD/BSS/raw Image,
а не только начало символа.

Используется только известная физическая память загруженного образа.
Чужой C-указатель не считается PA. CANDIDATE/REVIEW не читаются пробами и не
выдаются; boot pool не допускается и не используется. Нет общего PMM/heap,
reclaim или передачи общей RAM; смысл `GRANTED=0` остаётся прежним.

## Три адресных пространства и права

SAFE — отдельный привилегированный корень без пользовательских отображений.
Он нужен диспетчеру и очистке учёта. A и B имеют собственные корни. Все три
сохраняют supervisor-only замыкание кода/данных ядра, таблиц, метаданных,
привилегированных стеков, exception path и UART. Эти image mappings могут
оставаться RWX для ядра; системный W^X этим опытом не заявляется.

| Пользовательский VA | Корень A | Корень B | Права пользователя |
|---|---|---|---|
| `0x10000000–0x10001000` | Code A PA | Code B PA | Read/execute, не write |
| `0x11000000–0x11001000` | Stack A PA | Отсутствует | Read/write, не execute |
| `0x11010000–0x11011000` | Отсутствует | Stack B PA | Read/write, не execute |
| `0x12000000–0x12001000` | Data A PA | Отсутствует | Read/write, не execute |
| `0x12010000–0x12011000` | Отсутствует | Data B PA | Read/write, не execute |

Одинаковый VA кода обозначает разные физические code pages под разными roots.
Код/данные/стек другого процесса не получают пользовательского alias. Identity
отображения этих страниц внутри полного образа доступны только ядру; они
не дают пользователю дополнительных прав. Проверяются фактические таблицы,
эффективные права уровней и полный набор user leaves, включая отсутствие
чужих приватных страниц. Известный адрес отказа A — `UP_DATA_B_VA`, который
существует под B и отсутствует под A.

Бинарный fault PC вычисляется как `UP_CODE_VA + (fault_label - code_a)`.
Физический адрес исходного ASM-symbol в образе и пользовательский PC различны.
PE relocation относится к размещению физического образа; пользовательские VA
эксперимента фиксированы. Доказательство связывает exact opcode и offset
символа с конечными PE/ELF/Image и SHA загружаемого артефакта.

## Контекст входа и диспетчер

`struct up_context` содержит **все целочисленные GPR и поля пользовательского
кадра возврата**, наблюдаемые на аппаратном входе, а не контекст T-P1.6 на
границе C-вызова:

- `gpr[31]`: ARM X0–X30; x86 первые 15 слов — RAX, RBX, RCX, RDX, RSI,
  RDI, RBP, R8–R15, остальные слова детерминированно нулевые;
- SP offset 248, PC offset 256, status offset 264;
- CS offset 272 и SS offset 280 — реальные x86 selectors; на ARM нулевые;
- полный размер — 288 байт.

Отдельное событие хранит kind, vector, syndrome, fault VA, фактический active
root и привилегированный SP входа. Архитектурный код проверяет происхождение
и только затем превращает аппаратное событие в YIELD, EXIT или FAULT. Ядро
не принимает сырой пользовательский указатель для произвольного чтения или
записи. Снимки приватных данных читаются по заранее доказанным известным
image-owned объектам.

Диспетчер сохраняется на исходном стеке ядра. `up_arch_run()` входит в CPL3/EL0,
захватывает exception frame и возвращается только после активации SAFE-root
на исходный dispatcher SP. Сохранение машинного frame и возврат вызывающему
C-коду — два разных механизма. Готовность SAFE-пути проверяется до user entry.

## x86-64: CPL3 и собственный путь входа

Поддерживаемый UEFI/OVMF-профиль проверяет long mode, четырёхуровневую
трансляцию, физическую ширину, NX/PAT и доступность полного образа по старым
таблицам до замены root. Новые GDT/IDT/TSS находятся в допущенном образе.
GDT задаёт kernel CS `0x08`, kernel data `0x10`, user data `0x1b`, user code
`0x23` и TSS selector `0x28`. Accessed у сегментов установлен заранее;
аппаратуре не требуется изменять старые firmware descriptors.

При замене GDTR прежняя IDT ещё кратковременно действует. До новой IDT
сохраняется совместимый временный alias прежнего kernel CS в собственной GDT;
его селектор и все старые gates заранее проверены. После загрузки новой IDT,
чьи gates используют CS `0x08`, предел GDTR сужается до 55. Это сохраняет
диагностический путь при смене дескрипторов; новое пользовательское выполнение
начинается только после завершения подготовки и проверки SAFE-root.

TSS имеет архитектурные 104 байта, `RSP0` указывает на верх отдельного
16384-байтного entry stack, IST не используется. `iomap_base=104` за пределом
TSS limit 103 запрещает пользовательский port I/O при IOPL=0. Новый IDT
разрешает из CPL3 только gate `INT 0x80`; `#PF` остаётся DPL0 hardware gate,
и `INT 14` из user mode не может имитировать ожидаемый fault. Неожиданные
векторы ведут в терминальную раннюю диагностику с новым kernel CS.

Начальный IRETQ frame содержит действительные user CS/SS, собственный user
RSP, entry RIP и RFLAGS `0x2`: IF=0, DF=0, IOPL=0. Изменения арифметических
flags пользовательским кодом допустимы; небезопасные управляющие flags не
принимаются. Вход INT/#PF меняет CPL и получает RSP0 из TSS независимо от
user RSP. Сохраняются все 15 GPR, нормализованные vector/error и hardware
RIP/CS/RFLAGS/RSP/SS до C-обработки; C вызывается по Microsoft x64 ABI с
выравниванием и shadow space.

Сырой entry frame после сохранения GPR имеет смещения: vector 120, error 128,
RIP 136, CS 144, RFLAGS 152, user RSP 160, SS 168; всего 176 байт.
Происхождение CPL3 проверяется **до использования** user RSP/SS. При kernel
`#PF` сохраняются реальные vector/PC/error/CR2 и выполняется аварийный старый
diagnostic path; это не событие FAULT пользовательского слота.

Тестовый INT требует RAX=1 для yield либо RAX=2 для exit и точного ожидаемого
PC продолжения. Fault A — настоящий vector 14, hardware error `0x4`
(non-present, user, read; без write/execute/RSVD), CS RPL3,
`CR2=0x12010000` и точный RIP встроенного чтения. Активный CR3 фиксируется
до возврата; затем включается SAFE CR3, очищаются соответствующие TLB
зависимости и восстанавливается исходный dispatcher stack. x86 NX запрещает
исполнение data/stack; U/S проверяется на всех необходимых уровнях.

## AArch64: EL0 и собственные EL1-векторы

Неизменённый startup приводит initial EL1 и EL2→EL1 к EL1h с MMU/cache off.
Новый профиль отдельно проверяет гранулу/PA width и строит свои stage-1
таблицы: TTBR0, 48-bit VA/L0, 4-КиБ pages, ASID0, TTBR1=0/EPD1, без TBI.
MAIR `0x44` задаёт Normal-NC и Device-nGnRnE; PL011 остаётся отдельной
привилегированной NX device page. Переключение roots сопровождается
барьерами и инвалидацией EL1 TLB, фактический TTBR0 читается обратно.

User code имеет AP=3, PXN=1, UXN=0; user data/stack AP=1, PXN=1, UXN=1.
Остальные image mappings доступны только EL1. Первичный ERET устанавливает
EL0t, masked DAIF (`SPSR=0x3c0`), собственные SP_EL0 и entry ELR. FP/SIMD
инструкции и их общий context не входят в контракт.

Новая таблица VBAR содержит 16×128 байт с выравниванием/размером 2048.
Нижний AArch64 synchronous slot 8 сохраняет X0–X30, SP_EL0, ELR_EL1,
SPSR_EL1, ESR_EL1 и FAR_EL1 до C-обработки. Исключение использует
привилегированный SP_EL1, а не недоверенный SP_EL0. Верхний/current-EL fault
или unsupported slot остаётся терминальным diagnostic path.

Сырой 320-байтный кадр содержит X0–X30 по offsets 0–240, SP_EL0 248,
ELR 256, SPSR 264, ESR 272, FAR 280, TTBR0 288, фактический SP входа 296,
номер vector 304 и нулевое reserved-слово 312. Сначала сохраняются все GPR,
затем читаются специальные регистры. Этот кадр находится на entry stack;
сохранённый AAPCS64-контекст C-диспетчера остаётся на первоначальном стеке.

Тестовые SVC `#1`/`#2` обозначают yield/exit и требуют того же значения X0,
происхождения EL0t и точного continuation PC. Fault A требует EC `0x24`
(Data Abort из нижнего EL), SPSR mode EL0t, read, достоверного FAR,
`FAR=0x12010000` и точного ELR инструкции LDR. Поскольку таблица L3 существует
для data A, отсутствующий leaf data B даёт translation DFSC `0x7`
(ожидаемый ESR `0x92000007`). Instruction abort, current-EL abort, permission
fault другого вида, FnV или другой VA/PC не принимаются. После захвата
включается SAFE TTBR0, выполняется TLB/barrier sequence и возвращается
исходный dispatcher SP_EL1; fault A не возвращается в EL0.

## Допустимый сценарий и завершение

Слоты имеют состояния FREE, READY, RUNNING, FAULTED и EXITED. Кооперативный
диспетчер выбирает READY; YIELD возвращает RUNNING в READY, ожидаемый fault
переводит только текущий A в FAULTED, штатный выход B — в EXITED. Неверный
current, происхождение, операция, переход, диапазон или переполнение вызывает
отказ без частичного изменения живых слотов. Терминальные слоты не выбираются.

Обязательный смысловой порядок:

1. A действительно выполняется в user mode и уступает через аппаратный вход.
2. B выполняется на своём стеке, записывает `0x123456789abcdef0` в свою data page
   и уступает. Сохраняются его полный контекст, продолжение и данные.
3. A возобновляется и выполняет известное чтение B-private VA. CPU порождает
   ожидаемый user read translation fault на точной инструкции.
4. Архитектурный вход захватывает кадр и возвращается под SAFE-root на исходный
   стек. После проверки аппаратного события ядро переводит только A в FAULTED.
   Аварийный PC A не используется для нового user entry.
5. B возобновляется **после fault A**, проверяет прежнее значение, меняет его
   на `0xfedcba9876543210` и штатно выходит через аппаратный вход.
6. После возврата под SAFE-root терминальные контексты выводятся из употребления
   и освобождается только учёт слотов. Страницы остаются в резерве образа.
   Ядро проверяет завершённую последовательность, dispatcher cookie, roots,
   данные и отсутствие повторного выбора A; только затем PASS и обычный halt.

Обе программы кладут cookie на собственный user stack. B дополнительно
сохраняет известный шаблон `0x55aa001122334455` в volatile R10/X9 перед yield
и проверяет его после возобновления, вместе с nonvolatile R12/X20 и значением
стека/приватных данных. Поэтому эксперимент наблюдает сохранение volatile
регистра аппаратного кадра, а не только регистра, который должен сохранять
обычный C-вызов. Проверка сырых GPR/stack snapshots со стороны ядра и runner
отдельна от инструкций сравнений самой B.

Неверная инструкция, VA, процесс, происхождение exception, порядок или syndrome
не засчитываются как ожидаемый fault. Неожиданное исключение самого ядра
остаётся диагностируемым аварийным отказом. Нет возврата из kernel fault,
автоматического перезапуска или гарантии диагностики повреждённого kernel stack.

## Доказательства и непроверенные свойства

Host-тесты проверяют переходы, отказы и неизменность состояния; они не доказывают
CPL3/EL0. Strict UART parser требует аппаратные origin fields, полные диапазоны,
активные roots, продолжения/данные B до и после fault, точные PC/VA/syndrome,
safe-root cleanup, итоговый PASS и halt. Он отвергает ложный origin, чужой fault,
выход B до fault, повторный выбор A и PASS-only. Timeout/reset/тишина не PASS.

Три обязательных новых QEMU jobs — x86-64/OVMF, ARM virt initial EL1 и
initial EL2→EL1. Результат каждого связывается с manifest, бинарными SHA и
декодированным integer-only кодом. Общий FP/SIMD-контекст не сохраняется.
Сначала повторяется точная база тем же toolchain; затем проверяются все прежние
артефакты, включая T-P1.6, и четыре ordinary reproducibility outputs. Фактические
числа публикуются в отчёте, а не выводятся из старого счётчика 36.

Это проверка сдерживания **одного заранее выбранного user memory fault**.
Она не доказывает стойкость против враждебного кода, отсутствие side channels,
production W^X, generic process ABI, безопасность всех операций ядра или
восстановление после ошибки ядра. Нет общего FP/SIMD, IRQ/таймера/вытеснения,
SMP, IPC, драйверов, приложений, GUI или Deep Drop. T-P1.8 не начинается.

Владелец отдельно сообщил T-P1.6 Android/Termux 39/39 PASS, код 0, проверенный
SHA `d8065f31ae292eccd2558ddc8dc2cd91b78b855f`, оба ARM task jobs PASS по
скриншотам; предварительный LLVM objdump — 21.1.8, QEMU version не показана,
сырые UART/JSON не приложены. Это история предыдущего этапа. T-P1.7 Android,
VirtualBox и физические устройства остаются SKIPPED до отдельных запусков.

Публикуется только task branch. `main`, прежние refs, `docs/styleos-readme`,
корневой README, Portable-os и старые отчёты/checksums не изменяются. Нет merge,
force push или release. После отчёта и публикации работа останавливается.

Архитектурные источники: [Intel SDM, System Programming Guide](https://www.intel.com/content/www/us/en/developer/articles/technical/intel-sdm.html),
[Arm AArch64 Exception Model](https://developer.arm.com/-/media/Arm%20Developer%20Community/PDF/Learn%20the%20Architecture/Exception%20model.pdf).
