# ADR-0003: минимальный HAL ранней диагностики

Дата: 12.11.2026. Статус: интерфейс прототипа T-P1.0. Источник — `include/styleos/arch.h`.

## Контекст

Первое C-ядро должно одинаково сообщить о полученном управлении на двух ISA. Firmware console после UEFI `ExitBootServices` недоступна, а у AArch64 `virt` своя карта устройств. До появления планировщика, аллокатора и IRQ-драйверов полезна синхронная ранняя консоль.

## Решение

Общий код использует четыре функции:

```c
void arch_console_init(void);
void arch_putc(char ch);
void arch_puts(const char *text);
_Noreturn void arch_halt(void);
```

x86-64 адаптер выполняет портовый I/O COM1; AArch64 адаптер использует MMIO PL011 платформы QEMU `virt`. Код C-ядра не содержит UEFI-вызовов или UART-регистров конкретной платформы. Остановка выполняется архитектурным кодом; вызов не возвращает управление в уже завершённую UEFI boot environment.

Polling-вывод выбран ради наблюдаемости старта, а не как производительная конечная консоль. В нём нет планирования, очередей ввода, пользовательского TTY, драйверной модели, обещаний потокобезопасности или гарантий вывода при любой неисправности UART.

## Отказы и тестовые пределы

Ошибку handoff следует диагностировать настолько рано, насколько доступен UART, затем остановиться. Провал подготовки UEFI memory map или `ExitBootServices` не должен переводиться в обычный `kernel_main`. Unsupported EL на ARM — отдельный неуспешный старт.

Host-тест может проверить выбор ошибки и формат логики без доступа к устройству. Только target smoke в эмуляторе проверяет реальные инструкции port I/O/MMIO и переход в C-ядро. Даже успешный target smoke не доказывает доступность того же COM1/PL011 на физической машине.

## Будущие решения

Прерывания, framebuffer, буферизованная консоль, уровни журналирования, драйверные службы и модель ядра требуют отдельных решений. Существующий `arch.h` — узкий шов между C-прототипом и аппаратным стартом, а не законченная HAL для всех будущих устройств.
