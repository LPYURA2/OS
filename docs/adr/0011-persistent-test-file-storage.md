# ADR-0011 — сохраняемый тестовый файл через VirtIO Block MMIO

Статус: ограниченное решение T-P1.8A в `feature/styleos-t-p1-8a`, база
`2831e6a1c54562d1f37518913f07e648cc00cc2d`. Это первый эксперимент с
сохранением небольшого файла между независимыми запусками VM, без выбора
промышленной файловой системы, модели ядра или пользовательского ABI.

## Причина и границы

T-P1.7 проверил конкретный пользовательский fault и продолжение второй
программы. Он не создавал файла на диске. Новый отдельный `--test-storage`
проверяет цепочку guest → блочное устройство → файл диска QEMU → новый guest.
Само содержимое файла и его метаданные создаёт машинный код StyleOS.
Python подготавливает пустой тестовый диск и управляет процессами QEMU.

Новый путь разрешён только для AArch64 QEMU `virt`, одного CPU и одного
VirtIO Block MMIO устройства. x86-драйвер, внешние программы, рабочий стол,
SDK, `.tea`, Deep Drop, готовый пользовательский образ и T-P1.8B не входят
в решение. Старые профили, `boot_info v1`, нормализация памяти, штатные
загрузочные пути и исторические свидетельства сохраняются.

`--test-storage` имеет отдельный output и несовместим со всеми прежними
тестовыми флагами. Обычный образ не инициализирует новый драйвер и не пишет
на подключённый диск. Новые исходники и статические объекты отсутствуют
в прежних образах; это проверяется сравнением с точной базой тем же toolchain.

## Фиксированный аппаратный стенд

Используется AArch64 `virt`, `cortex-a57`, TCG, один CPU, polling UART,
без графики, сети, root, OVMF и x86-инструментов. Загрузочный raw Image и
диск данных — разные обычные файлы. Disk backend не использует snapshot
или restore: следующий процесс QEMU открывает тот же путь диска данных.

VirtIO transport — современный MMIO version 2. Требуются
`VIRTIO_F_VERSION_1` (bit 32) и `VIRTIO_BLK_F_FLUSH` (bit 9);
read-only feature bit 5 отвергается.
Неподдержанный transport, отказ feature negotiation, недостаточная
вместимость, неверные границы или отсутствие flush останавливают тест.
Они не заменяются объявлением о якобы сохранённых данных.

QEMU запускается с `-global virtio-mmio.force-legacy=false`; data backend
задаётся file/raw block nodes с включённым flush (`no-flush=false`) и
`virtio-blk-device`. Точная фактическая команда сохраняется в каждом job.

MMIO-диапазон и управляющая фаза берутся из проверенного DTB выбранного
QEMU-профиля. Это отдельный ограниченный parser для `virtio,mmio` и
`/chosen/bootargs`, а не новое общее обещание поддержки любых FDT bus/ranges.
Исходник DTB остаётся read-only и должен целиком лежать в уже доказанном
`SOURCE` диапазоне. Поддерживаются root address/size cells 2/2 и только
прямые root nodes с `virtio,mmio`: 16-байтный `reg`, base в
`[0x0a000000,0x0a004000)`, размер/шаг `0x200`, не более 32 разных spans.
Драйвер читает
только допустимый объявленный MMIO span и выбирает единственное подходящее
block device; произвольный перебор адресов RAM/устройств не нужен.

## Память устройства и видимость

Очередь, request/bounce storage и управление статически входят в загруженный
образ и сохраняют его резерв. После handoff, до инициализации storage-профиля
и передачи буферов DMA, доказываются целые интервалы,
размер, выравнивание, отсутствие переполнения и перекрытия с kernel stack,
handoff, DTB, diagnostic workspace, boot pool/metadata, vectors и друг с другом.
Бинарное доказательство независимо проверяет ELF symbols, writable BSS,
identity PT_LOAD, обе границы очистки BSS и полный размер raw Image.

Этот профиль работает в поддерживаемом EL1 с MMU и caches выключенными,
маскированными IRQ и известным фиксированным ARM Image. Аппаратный adapter
проверяет состояние до обращения к DMA. PA выводятся только для конкретных
доказанных image-owned объектов. Приведение произвольного C-указателя в PA
не является интерфейсом драйвера. Пользовательский указатель устройству не
передаётся: данные копируются через собственный ограниченный bounce buffer.

Три 4096-байтных объекта `styleos_vblk_control`, `styleos_vblk_queue` и
`styleos_vblk_request` выровнены на 4096. Guest дополнительно имеет отдельные
4096-байтные control и workspace, также выровненные на 4096. В queue page
descriptor table начинается по offset 0 и имеет выравнивание 16, avail ring
— offset 256, used ring — offset 512. В request page header имеет offset 0
и размер 16, status — offset 64 с начальным sentinel 255, bounce sector —
offset 512 и размер 512.

Одна split virtqueue из восьми descriptors обслуживает один запрос за раз. Descriptor table,
available ring и used ring находятся в своём выровненном storage; размеры
очереди и общего числа запросов ограничены. Устройство получает header,
данные для READ/WRITE и отдельный status byte; FLUSH не подменяется обычной
записью. Направление descriptor rights соответствует тому, кто пишет память.

Перед публикацией available entry и notify выполняется требуемый barrier;
после наблюдения used index — barrier перед чтением результата и данных.
Polling имеет конечные пределы: 1000000 итераций на запрос, 10000 на reset,
не более 8192 submitted requests за boot. Проверяются использованный
descriptor id=0, изменение индексов, status=0 и used length: 513 для READ,
1 для WRITE/FLUSH. NEEDS_RESET, FAILED, timeout или неправильный status
делают транспорт непригодным для дальнейшего успешного теста. Это single-CPU механизм
без IRQ-handler, cache-coherent общего allocator или SMP-синхронизации.

Нет выдачи CANDIDATE/REVIEW, общего PMM/heap, reclaim или allocation из старого
boot pool. `GRANTED=0` сохраняет прежний смысл: наличие нового устройства не
передаёт ядру общую RAM.

## Минимальный формат и фиксация

Общий storage layer отделён от MMIO через ограниченные sector READ, WRITE
и FLUSH callbacks. Он хранит один небольшой именованный файл; каталоги,
POSIX API, файловые дескрипторы и совместимость со стандартной ФС не вводятся.
Числа кодируются явно little-endian, без зависимости дискового формата от
C struct padding. Сектор — 512 байт, тестовый диск имеет точно 2048 секторов
(1048576 байт), длина имени 1..31 байт, payload 0..1024 байт. Имя принимает
печатные ASCII-байты `0x21..0x7e`, кроме `/` и `\`; пути не поддерживаются. Все
неиспользуемые байты фиксированных записей и дополнения полей нулевые.

| Размещение | Поля и offsets в байтах |
|---|---|
| Superblock, LBA 0 | magic `STYSTR1\0` [0,8), version u32@8=1, sector bytes u32@12=512, disk sectors u64@16=2048, slot0 u64@24=2, slot1 u64@32=6, slot sectors u32@40=4, max payload u32@44=1024, max name u32@48=31, CRC u32@52; [56,512) нули |
| Slot A/B | Base LBA 2/6, четыре сектора: metadata offset 0, payload offsets 1..2, commit offset 3 |
| Metadata | magic `STYMETA1` [0,8), version u32@8, bytes u32@12=512, generation u64@16, length u32@24, name length u32@28, payload CRC u32@32, metadata CRC u32@36, slot index u32@40, slot base u32@44, [48,64) нули, name [64,96), [96,512) нули |
| Payload | 1024 байта; точные `length` байт файла с нулевым дополнением |
| Commit | magic `STYCMT1\0` [0,8), version u32@8, bytes u32@12=512, generation u64@16, length u32@24, metadata CRC u32@28, payload CRC u32@32, slot index u32@36, slot base u64@40, commit CRC u32@48, [52,512) нули |

CRC32 — IEEE reflected polynomial `0xedb88320`, init/final xor `0xffffffff`.
В super/metadata/commit checksum вычисляется по всему сектору при нулевом
собственном CRC field. Payload CRC охватывает все 1024 байта с дополнением.
Generation начинается с 1; следующее значение после UINT64_MAX запрещено.
Два годных кандидата с одинаковым generation вызывают отказ вместо
произвольного выбора.

Формат использует две независимые области с поколением, именем, длиной,
metadata/payload integrity checks и отдельной записью фиксации. На старте
принимаются только целые зафиксированные кандидаты. Выбирается годное
актуальное поколение; повреждённая новая область не делает старую годную
версию недоступной. Если годной версии нет, возвращается явная ошибка;
распознанное пустое хранилище сразу после явной инициализации отдельно имеет
состояние EMPTY. Mount не стирает неизвестный или повреждённый диск.

Инициализация — отдельная операция только для созданного runner пустого
тестового диска. Она проверяет точную вместимость и читает все 2048 секторов,
требуя нулей во всём диске, затем пишет superblock и подтверждает его FLUSH.
Неизвестная сигнатура не является разрешением форматировать пользовательские
данные. Runner не умеет открывать произвольный переданный диск для записи.

Порядок обновления:

1. Выбрать неактивную область, сохранив текущую зафиксированную версию.
2. Записать нули в её commit sector и дождаться успешного FLUSH этой
   инвалидизации, прежде чем изменять metadata или payload.
3. Записать новую metadata и два payload sector с новым поколением и checksum.
4. Дождаться успешного FLUSH данных. Только после него подтвердить PREPARED.
5. Записать отдельную commit record, связанную с этой metadata и payload.
6. Дождаться финального успешного FLUSH. Только затем подтвердить COMMITTED.

Один полный save содержит пять sector WRITE и три FLUSH: инвалидизация,
данные, фиксация. Инициализация нового диска добавляет отдельные WRITE и
FLUSH superblock. Барьер PREPARED содержит четыре WRITE и первые два FLUSH;
новой commit record на диске ещё нет.

Промежуточное состояние после шага 4 не считается новой версией. Предварительная
инвалидизация нужна и при повторном использовании области после fallback.
Повреждённая новая версия может оставить старую commit record с тем же
поколением, которое будет снова выбрано после mount старой версии. Без
упорядоченного обнуления и FLUSH повторно подготовленные metadata/payload
могли бы совпасть с этой записью ещё до новой фиксации. После подтверждённой
инвалидизации такая запись уже не может подтвердить повторный save.
Generation и integrity binding дополнительно связывают новую фиксацию с данными.
Отказ callback/flush не превращается в успешное подтверждение.
Неопределённость после WRITE/FLUSH снимает mounted/prepared и текущий token;
продолжать save по прежнему состоянию памяти нельзя. Для нового решения о
текущей версии требуется read-only mount.

CRC обнаруживает выбранные повреждения формата и данных; это не защита от
злоумышленника, не подпись и не доказательство поведения реального накопителя
при отказе питания. Точные размеры и byte layout задаёт
`include/styleos/storage.h` и реализация `kernel/storage.c`.

## Сценарии и управление VM

Имя `note.txt` и байты обеих версий зашиты в guest:
`StyleOS note A\n` — 15 байт, `StyleOS note B: updated\n` — 24 байта.
Host задаёт только одну из ограниченных фаз через
`styleos.storage=init-a|read-a|update-b|read-b|prepare-b|recover-a`.
Для успешного чтения guest сравнивает имя, длину и каждый
байт, затем выдаёт результат. Read из RAM того же процесса не является
доказательством persistence.

Основная цепочка `persist-init-a → persist-read-a → persist-update-b → persist-read-b`:
свежий пустой диск → guest сохраняет A и подтверждает
финальный FLUSH → первый процесс QEMU полностью останавливается → новый
процесс читает A → guest обновляет B с финальным FLUSH → ещё один процесс
читает именно B. Во всех запусках используется один и тот же обычный файл
диска, без host-side создания содержимого или исправления между фазами.

Вторая цепочка `crash-init-a → crash-prepare-b → crash-recover-a` использует
отдельный свежий диск. Guest сначала фиксирует A.
Следующий guest обнуляет commit неактивной области с отдельным FLUSH, затем
пишет B и подтверждает FLUSH данных. На барьере до записи новой commit record
он навсегда прекращает запись и не выдаёт итоговый PASS. Runner распознаёт
точный барьер и принудительно
останавливает именно этот процесс QEMU. Новый процесс открывает неизменённый
host диском файл и обязан прочитать целую A; B либо смесь не принимаются.

Неожиданный exit/reset, timeout, error или PASS без полного контракта не
засчитываются как ожидаемое прерывание. Управляемое прекращение QEMU на
барьере не является проверкой отключения питания телефона, host или
физического диска. Во время барьера нет продолжающейся записи commit.

## Безопасность runner и свидетельства

Одна команда `CC=clang python tools/test_storage.py --output build/termux-tp18a`
сама выполняет host-проверки, собирает отдельный boot image, создаёт два
тестовых диска и запускает семь независимых процессов QEMU без ручного
форматирования и переноса файлов. Storage-путь не требует LLVM objdump,
OVMF или x86 tools. Каждый запуск получает
новый собственный каталог внутри указанного output. Создание файлов
исключительное; повтор не затирает прежние диски, журналы или пользовательские
данные. Каталоги имеют вид `run-<UTC>-<random>`, диски создаются только под
их `disks/` как regular files с `O_EXCL|O_NOFOLLOW`. Output symlink и
не-каталог отвергаются. Открытие raw block devices, ранее существовавших образов для
форматирования и запись за пределы созданного каталога не входят в интерфейс.

UART/JSON фиксируют точные команды, стадии/процессы VM, phase, MMIO/device
features/capacity, операции транспорта, последовательность flush/commit,
generation/name/length/байты файла, контрольные барьеры и terminal lifecycle.
SHA boot image, manifest, бинарного evidence и диска до/после связывают запуск
с конкретными файлами. Read-only фазы не должны менять файл диска.
Сохраняются `test-results/results.json`, поэтапные `.log/.json/.uart`,
`run.json` и `provenance.json`. Для обычного PASS+HALT marker необходима
200-мс observation window, затем runner делает SIGTERM. Только правильный
подтверждённый pre-commit barrier, неподвижный ещё 200 мс, допускает
запланированный SIGKILL с return code -9.

Host-модели отдельно проверяют повреждённые signatures, metadata bounds,
length/checksum, fallback, повторную подготовку после fallback с инвалидизацией
старой commit record и отсутствие годной версии; они не называются
реальным отказом устройства. Transport model отдельно имитирует negotiation,
capacity, bounds, timeout и status errors. QEMU jobs подтверждают только
фактически выполненные обмены с эмулируемым устройством.

Фактические числа, версии, команды, SHA, UART/JSON и причины
PASS/FAIL/SKIPPED публикуются в [отчёте T-P1.8A](../test-results/t-p1-8a/README.md).
Новый Android/Termux, VirtualBox и физическое оборудование остаются SKIPPED
до соответствующих запусков. Owner-reported T-P1.7 Android 43/43, exit 0,
QEMU 11.1.3, SHA `af898029ff71892d8e3c6a3308263624af722130`, по трём
скриншотам учитывается отдельно; сырых UART/JSON нет. Это не результат T-P1.8A.

Публикуется только task branch. После отчёта работа останавливается до приёмки
1.8A владельцем. T-P1.8B и дальнейшая разработка не начинаются.
