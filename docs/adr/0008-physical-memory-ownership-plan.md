# ADR-0008 — проверяемый план владения физической памятью

Дата: 14.11.2026. Статус: ограниченное решение T-P1.5 в `feature/styleos-t-p1-5`, база `8bc7e78592c1aef78429042658f9ae02f71637c5` из T-P1.4. Это read-only план защиты и отказов, без передачи общей RAM и без выбора модели ядра.

## Фаза и смысл результата

Отдельные `--test-ownership-plan` и `--test-ownership-plan-invalid` работают после успешных handoff и MEMMAP на прежнем загрузочном пути. x86 сохраняет унаследованный CR3; ARM остаётся в EL1 с MMU off после начального EL1 либо EL2 → EL1. Новый код не переключает CR3/MMU, не меняет GDT/IDT/VBAR, не включает IRQ. `boot_info v1`, нормализация, boot pool, исключения и все профили T-P1.4 сохраняют прежнюю семантику.

| Статус | Проверяемое утверждение | Чего он разрешает |
|---|---|---|
| `PROTECTED` | Страница покрыта базовым резервом или доказанным живым диапазоном; указаны причина и происхождение | Запрет будущей выдачи. Это не утверждение о текущих правах отображения |
| `REVIEW` | Проверенный диагностический кандидат после вычитания защиты; причина `no-transfer` | Только рассмотрение в будущем этапе. Ни чтение пробой, ни запись, ни выдача не разрешены |
| `UNCLASSIFIED` | Адрес вне покрытого объединения либо вне известного набора источника | Положительного вывода о свободной памяти нет; все дыры перечислять не требуется |

Успешный план структурно валиден: его диапазоны, источники и зависимости согласованы. **`granted=0` всегда**, в том числе на ARM при `unresolved=0`. API не возвращает REVIEW как доступные страницы. Отсутствие неразрешённых зависимостей в узком профиле не заменяет процедуру передачи владения.

Неполнота известного набора старых таблиц и прочих firmware-зависимостей на x86 явно помечена `unresolved=3`: маска 1 — `TABLE_SET_INCOMPLETE`, маска 2 — `OTHER_FIRMWARE_STATE`. Структурно валидный план с этим статусом не допускает положительного заключения о передаче конкретной REVIEW-страницы. Отсутствие обязательного диапазона, противоречие VA/PA, ошибка карты, источника, границ, режима или ёмкости — уже не неопределённость: это отказ **до публикации** плана.

## Источники и базовые исключения

Исходные данные — проверенный `boot_info` и внутреннее read-only `boot_memory_evidence` успешной диагностики. Размер `-m` QEMU не подменяет UEFI map или DTB: runner использует его только как независимую проверку выбранного сценария.

* UEFI: исходные дескрипторы `GetMemoryMap`, реальные Loaded Image base/size после `ExitBootServices`, stride/version карты. В диагностическую RAM проходят только `EfiConventionalMemory` с WB и поддерживаемыми атрибутами. Loader/Boot Services/Runtime Services, неизвестные типы и неподходящие атрибуты остаются RESERVED даже при отсутствии отдельного живого claim. Завершение Boot Services не считается reclaim.
* FDT: поддерживаемые `memory`-узлы, полный проверенный `totalsize` DTB, reserve map и статические `reg` в `/reserved-memory`. Наличие `no-map` или `reusable` не отменяет резерв. Динамический резерв без подтверждённого размещения, неподдерживаемые cell/ranges-схемы и противоречивые данные вызывают отказ существующего парсера. За пределами описанной RAM/резервов вывод о памяти не делается.
* Архитектурный снимок: фактические регистры режима/root, GDTR/IDTR/CS либо VBAR/DAIF, плюс ограниченные подтверждённые зависимости. Число, похожее на адрес, само по себе не является доказательством доступности PA.

## Владелец, происхождение и срок жизни

Все диапазоны — физические полуинтервалы `[start,end)`. VA хранится отдельно от PA. Ниже «до отдельного решения» означает, что этот этап не содержит освобождения или передачи.

| Объект / источник | Владелец в снимке | Фаза и происхождение PA | Срок защиты |
|---|---|---|---|
| Полный образ с BSS, кодом и константами | Загруженный образ StyleOS | x86: реальный Loaded Image + проверенное identity; ARM: ELF VMA=LMA, BSS и объявленный Image extent | Весь текущий boot, без reclaim частей образа |
| Стек 65536 байт | Раннее ядро | Полные linker bounds внутри образа; текущий архитектурный путь | Пока исполняется ядро/exception path |
| Handoff 96 байт | Загрузочный адаптер, заимствован ядром | x86: статический объект в PE; ARM: живой объект на собственном стеке | До отдельного решения; `boot_info v1` неизменён |
| Исходная карта UEFI / весь DTB | Firmware / загрузчик | Проверенные границы источника из handoff и диагностики | До отдельного решения, независимо от дальнейших чтений |
| Workspace диагностики 12400 байт | Диагностика карты | Статический `diagnostic`, размер map + evidence, полный extent внутри образа | Пока используются снимок и его происхождение |
| Workspace плана 65536 байт | Только metadata плана | `styleos_ownership_workspace`, union в BSS, выравнивание 4096, полный бинарный extent | Весь текущий boot |
| Boot pool 32768 и metadata 4096 байт | Отдельный image-owned пул T-P1.3 | Два полных выровненных объекта внутри образа | Сохраняются; в этом профиле пул **не допущен** и не выдаёт страницы |
| Базовые RESERVED, включая неизвестные UEFI-типы и FDT-резервы | Прежние владельцы / политика источника | Неизменённый диагностический парсер и нормализатор | До явной передачи в будущем этапе |
| x86: действующая GDT | Firmware, используется CPU | GDTR/CS и реальный VA→PA по старому walker; полный PA-резерв до чтения | Пока зависит текущий exception/CS path; новой GDT нет |
| x86: IDT 4096 байт | Ранний exception path | IDTR и бинарный `early_idt`, identity внутри образа | Пока используется exception path; 16-byte alignment может покрыть две 4-КиБ страницы |
| x86: root и посещённые старые table pages | Firmware, всё ещё активны | CR3 и только дети из его реальных дескрипторов; baseline RESERVED до чтения | Пока активна эта трансляция; перечисление явно неполное |
| ARM: EL1 vectors 2048 байт | Ранний exception path | VBAR, executable ELF/raw Image и identity при MMU off | Пока используется текущий VBAR |
| ARM: страница PL011 | Устройство, MMIO | Фиксированный поддерживаемый QEMU virt профиль `0x09000000–0x09001000` | Пока используется ранний UART; это не RAM |
| T-P1.4 tables/control/data | Отсутствуют в этом профиле | `paging=not-built`; binary proof отвергает их символы | В будущей интеграции полные image-owned extents должны входить в защиту |

Вложенные объекты не суммируются повторно: защита образа уже включает стек, BSS и metadata. Отдельные claims сохраняют происхождение, а итог считает объединение страниц. Source и firmware-зависимости могут лежать вне образа; это не даёт права обращаться к произвольной общей RAM.

## Границы, ёмкость и публикация

`op_build()` потребляет числовые свидетельства и не разыменовывает PA. Проверяются размеры, оба конца, переполнение, физическая ширина, сортировка, обязательные claims, известные виды доказательства и согласованность перекрывающихся VA/PA. Карта повторно проверяется неизменённым нормализатором на копии. Неизвестный тип источника/claim либо потеря известного живого диапазона дают отказ.

Базовые RESERVED и живые claims округляются наружу до 4096 и объединяются, включая соседние интервалы. REVIEW берётся из диагностических кандидатов, округлённых внутрь прежней политикой, после вычитания полного PROTECTED. Приоритет защиты выше REVIEW. Выход отсортирован, интервалы не пересекаются; счётчики страниц относятся к объединению.

Лимиты фиксированы: 96 claims, 512 выходных диапазонов, 64 посещённые table pages и 66 сохранённых walk paths. Весь постоянный input/output/scratch находится в 65536-байтном image-owned workspace; обычные C locals используют существующий image-owned стек. Исчерпание лимита не урезает известный живой набор до удобного подмножества: публикуется ошибка. Промежуточные расчёты могут существовать в своей metadata, но до полного успеха наружу не выводятся claims, PROTECTED/REVIEW или PASS. При отказе выход невалиден, количества и `granted` равны нулю.

Записи нового кода ограничены собственной metadata и обычным стеком; прежний UART остаётся устройством вывода. Адреса из плана не используются для пробного чтения, записи, обнуления, выделения или освобождения страниц. Проверка BSS загрузчиком и прежняя диагностика выполняют прежние обязанности C-окружения; новый план не становится владельцем их источников.

## x86: чтение унаследованных зависимостей

Поддерживается узкий UEFI x64/OVMF профиль ADR-0007: long mode, четыре уровня, проверенные PA-width/NX/PAT, без неподдерживаемых PCID/LA57 и иных зависимостей. Фактический CR3 сохраняется. Каждая table page до первого чтения должна целиком находиться в baseline RESERVED и не пересекать CANDIDATE. Дети берутся только из реально прочитанных дескрипторов активного пути. Это не обход произвольных физических указателей.

Физический доступ для этих чтений остаётся явной предпосылкой поддерживаемого UEFI x64 профиля. Ограниченное identity-замыкание затем проверяет отображение каждой посещённой table page. Все image pages проверяются adapter на identity; GDT VA переводится отдельно, а её байты читаются только после доказательства отображений и полного PA-резерва. IDT/gates, CS и executable цели также проверяются. ПО не пишет GDT, таблицы или Accessed-биты; аппаратные A/D могут изменяться при обращениях и не считаются новым правом владения.

UART `WALK/STEP` сохраняет реальные дескрипторные пути для GDT и identity посещённых table pages. Общий код и runner независимо воспроизводят эти пути, проверяют root, ширину, уровни, large leaves, PA, PAT и непротиворечивость общих слотов с учётом аппаратных A/D. Это свидетельство **заявленного частичного набора**, а не дамп всех image leaves и не доказательство всего дерева старых таблиц. Firmware может иметь другие активные страницы и состояние: поэтому `unresolved=3` обязателен даже после PASS.

Снимок AFTER требует прежние CR0/CR3/CR4/EFER/PAT/GDTR/IDTR/CS и значимые условия IF/DF. Обычные арифметические flags C-кода могут отличаться. COM1 использует port I/O, отдельного MMIO claim x86 нет.

## ARM: отдельная фаза MMU off

Начальный EL1 и EL2 → EL1 используют прежний startup. Adapter проверяет реальный EL1, MMU/cache/endian состояние, DAIF, VBAR, стек и поддерживаемую PA-width. Для известных объектов полного ELF/BSS/Image физический адрес совпадает с адресом исполнения. `root=0` обозначает отсутствие активного stage-1 root в фазе MMU off; это не заявление о чтении, очистке или содержимом TTBR0.

Полный DTB и его FDT-резервы сохраняются. PL011 явно защищён как MMIO, а не добавлен в RAM. `unresolved=0` относится к этому заявленному QEMU virt набору; оно не доказывает поддержку нативного ARM-устройства или передачу REVIEW-страниц. При 128/256 МиБ источник диапазонов остаётся DTB, и runner требует соответствующее изменение реального входа.

## Соотношение с будущей фазой собственного root

Только прежние T-P1.4 paging-профили могут менять CR3/MMU. Новый план их не включает и не изменяет. При будущей явной интеграции надо защищать полный table reserve/control/data как живые объекты образа и фактически активный новый root. После нового CR3 прежние страницы не становятся свободными автоматически: остаются GDT/CS, firmware/source и иные остаточные зависимости, описанные ADR-0007. Смена root сама по себе не завершает передачу, не доказывает полное множество прежних таблиц и не разрешает reclaim. Для ARM MMU off и MMU on нужны разные явно обозначенные снимки.

## Наблюдаемая проверка и границы сдачи

`ownership-site.json` строится из PE/map либо ELF/raw Image с полными размерами, writable BSS/zero-fill, PT_LOAD identity, BSS clear/Image bounds и SHA. Отдельно проверяются diagnostic, стек, IDT/handoff или vectors, pool/metadata и их непересечение с workspace. Paging buffers и managed fault symbols запрещены. Для PE runner добавляет только фактический Loaded Image base к RVA.

Runner заново выводит бинарный proof, проверяет sidecar/manifest/загружаемые артефакты по SHA, затем независимо строит объединение защиты и разность REVIEW из MEMMAP и claims. Он проверяет источники, фазу, регистры до/после, допустимые причины и все опубликованные walk paths. Строка PASS без этого набора, выход за известную RAM/резервы, подменённый диапазон, ненулевой grant, лишняя или частичная публикация, timeout/reset/тишина не принимаются.

Контролируемый `--test-ownership-plan-invalid` снимает IMAGE proof (`claims[0].proof=OP_UNPROVEN`) только в собственном тестовом input. Реальные boot structures не портятся. Ожидается единственный ownership-итог `STYLEOS OWNERSHIP ERROR: required` после MEMMAP, без плана и PASS. Подробные команды и матрица — [TESTING](../TESTING.md); фактические результаты — [отчёт T-P1.5](../test-results/t-p1-5/README.md).

Прежние normal/negative/exception/pool/paging сценарии и четыре обычных воспроизводимых артефакта сохраняются. T-P1.4 имеет собственный Linux-отчёт 37/37, ARM64-only 27/27 и Python 101/101; новый телефонный отчёт T-P1.4 не получен. T-P1.5 Android/Termux, VirtualBox и физические устройства — SKIPPED до отдельных реальных запусков. Полный Linux и Linux ARM64-only не заменяют их.

Публикуется только task branch, без main, прежних refs, Portable-os, merge, force push и release. После отчёта этап останавливается. Общий PMM/heap, первый пул из общей RAM, reclaim, собственная GDT, IRQ/SMP, recovery, процессы/драйверы и модель ядра требуют отдельных решений.
