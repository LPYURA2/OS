# ADR-0012 — отдельная тестовая программа с виртуального диска

Дата: 17.11.2026. Статус: ограниченное решение T-P1.8B в
`feature/styleos-t-p1-8b`, база
`1ea8d090cd12c4a5d20f628c927fcba787aede98`. Фактические команды, результаты,
проверенный код и журналы находятся в [отчёте](../test-results/t-p1-8b/README.md).
Решение не выбирает модель ядра, production ABI или публичный формат приложений.

## Причина и граница

[ADR-0010](0010-user-process-fault-isolation.md) проверил аппаратный вход в EL0
и продолжение после пользовательского fault, но код программ входил в boot
image. [ADR-0011](0011-persistent-test-file-storage.md) проверил отдельный
сохраняемый файл через VirtIO, но не исполнял его. Новый профиль связывает эти
пути: обычные Clang/LLD отдельно собирают файл, host явно упаковывает его в
свежую фикстуру прежнего хранилища, а StyleOS сам монтирует диск, читает,
проверяет, копирует и исполняет полученные байты в EL0.

Только `--test-disk-app` на AArch64 QEMU `virt` получает это разрешение. У него
отдельный output, один CPU, polling и несовместимость со всеми прежними
тестовыми флагами. Обычная загрузка, `boot_info v1`, нормализация памяти,
старые профили и формат хранилища T-P1.8A сохраняются. x86-64 проходит прежние
регрессии; новый загрузчик и VirtIO-драйвер на x86 не портируются.

Нет PMM/heap, выдачи CANDIDATE/REVIEW, reclaim, использования boot pool,
общего планировщика, IRQ/таймера/вытеснения/SMP, FP/SIMD-контекста, файлового
API пользователя, IPC, сети, графики, SDK, `.tea` или готового VirtualBox-образа.
`GRANTED=0` сохраняет прежний смысл. После отчёта и публикации task branch
работа останавливается; следующий этап обсуждается отдельно.

## Отдельная сборка и неизменённое хранилище

Payload не линкуется в boot image и не передаётся через bootargs, UART или
разделяемую память. Исходник — семь integer-only AArch64-инструкций. Стандартные
Clang/LLD создают отдельно проверяемые ELF и raw code; host builder добавляет
тестовый контейнер. Краткая сборка вне дерева ядра приведена в
[TESTING](../TESTING.md#внешняя-программа-с-диска-t-p18b).

Явно обозначенный host-side упаковщик фикстуры использует прежний storage
layer и создаёт только новый 1-МиБ regular file в каталоге текущего прогона.
В хранилище находится единственный файл `app.bin`, generation 1. Superblock,
два slot, metadata, payload, commit и CRC имеют точный формат ADR-0011.
Это исключение разрешает host заранее положить внешний тестовый файл;
исторический T-P1.8A по-прежнему создаёт свои данные только в guest.

Каждый прогон получает новый `run-<UTC>-<random>` и три разных диска: вариант
A, вариант B и контейнер с неверным magic. Нет открытия пользовательского
диска, блочного устройства хоста, исправления существующей фикстуры или
повторного использования диска исторического прогона. Создание эксклюзивно;
существующий путь, symlink или неподходящий тип файла отвергается.

Guest предоставляет storage layer только READ. WRITE/FLUSH callbacks всегда
отказывают. Старый VirtIO-контракт требует VERSION_1 и FLUSH и отвергает
аппаратный RO feature: он не ослаблен ради нового режима. Поэтому backend
остаётся совместимым с прежним драйвером, а read-only свойство нового пути
проверяется нулевыми WRITE/FLUSH и одинаковыми SHA-256 диска до/после VM.
Это read-only эксперимент гостя, а не обещание аппаратного RO устройства.

## Узкий контейнер, а не публичный executable ABI

Все поля little-endian; файл имеет не более 1024 байт, включая фиксированные
32 байта заголовка. Контейнер не содержит VA/PA и не выбирает kernel address.
Гость владеет всеми адресами и конечными буферами.

| Offset | Поле | Поддерживаемое значение |
|---|---|---|
| 0..7 | magic | `STYAPP1\0` |
| 8..11 | version, u32 | 1 |
| 12..13 | ISA, u16 | 183, AArch64 |
| 14..15 | header bytes, u16 | 32 |
| 16..19 | code length, u32 | 28 для текущей закрытой грамматики |
| 20..23 | entry offset, u32 | 0 |
| 24..27 | reserved, u32 | 0 |
| 28..31 | CRC32, u32 | IEEE CRC32 всего файла с нулями в этом поле |
| 32..59 | code | семь 4-байтных AArch64-инструкций |

Общие численные пределы кода — 1..992 байта с кратностью четырём; длина
должна точно совпадать с длиной файла за вычетом header. Затем текущий loader
требует ровно 28 байт и декодирует каждую инструкцию закрытой грамматики:
`CBNZ X0,+12`, `MOVZ X1,#0x1201,LSL #16`, `LDR X2,[X1]`, `MOVZ X19,#low`,
`MOVK X19,#high,LSL #16`, `MOVZ X0,#exit`, `SVC #2`. Меняются только два
16-битных immediate маркера и 16-битный exit code. Padding, дополнительные
инструкции, косвенные переходы, FP/SIMD и произвольный ELF не принимаются.
Текущий полноценный файл имеет 60 байт.

Проверяются magic/version/ISA/header/reserved, полный размер, кратность,
entry, CRC, каждый opcode, арифметика указателей, выравнивание destination,
ёмкость и непересечение source/destination/info. Проверка завершается до
первого копирования или публикации `da_info`; отказ не оставляет частично
загруженной программы. Контейнер с корректными storage metadata/CRC и
неверным executable magic проходит mount/read и отвергается именно loader.
Ни до, ни после этого отказа EL0-входа нет.

## Допущенные статические ресурсы

| Объект | Полный размер |
|---|---|
| `styleos_disk_app_tables` | 2 × 32 × 4096 = 262144 байта, SAFE и USER |
| `styleos_disk_app_control` | 16384 байта, последние 4096 — arch scratch |
| `styleos_disk_app_entry_stack` | 16384 байта, доверенный EL1 exception stack |
| `styleos_disk_app_code` | 4096 байт, копия проверенного code |
| `styleos_disk_app_user_stack` | 4096 байт |
| Storage workspace | 4096 байт |
| Прежние VirtIO control/queue/request | По 4096 байт |
| Собственные EL1 vectors | 2048 байт с выравниванием 2048 |

BSS-объекты выровнены на 4096. До их первой записи после handoff/MEMMAP
доказываются полные интервалы, размеры, арифметика, RESERVED/image containment
и отсутствие перекрытия друг с другом, kernel stack, handoff, DTB, diagnostic
workspace, boot pool/metadata и старыми/новыми vectors. Полный ELF/PT_LOAD/BSS,
обе границы startup clear и raw Image проверяются независимо в
`disk-app-site.json`. Начало символа без доказанного конца недостаточно.
Это адреса только известных объектов фиксированного Image `0x40080000`;
общего преобразования C-pointer → PA нет.

## Переход от DMA к собственным таблицам

1. Поддерживаемый startup приводит initial EL1 либо EL2→EL1 к EL1h с MMU,
   D-cache и I-cache off, masked DAIF. Guest проверяет этот режим и полные
   допущенные DMA-объекты до обращения к VirtIO.
2. Ограниченный read-only FDT parser выбирает объявленные `virtio,mmio`
   диапазоны фиксированного QEMU `virt`; `styleos.diskapp=run|reject` выбирает
   только сценарий. Bootargs не содержит программу или её ожидаемые байты.
3. `st_mount` и `st_read` читают `app.bin` в конечную статическую память.
   Каждый READ возвращается только после проверенного успешного completion.
4. После последнего READ окно I/O закрывается. Проверяются завершение всех
   запросов, `avail.idx == used.idx == requests == reads`, bounded счётчик и
   `writes=flushes=0`; после полного barrier indices проверяются повторно.
   Ошибка I/O или неподтверждённый drain запрещает EL0.
5. Проверка контейнера и копирование кода происходят при MMU/cache off уже
   после drain. Выполняются `DSB SY; IC IALLU; DSB SY; ISB`, строятся собственные
   SAFE/USER roots и включается EL1 stage-1 с caches off. MMIO VirtIO в новом
   замыкании отсутствует. После drain нет новых device I/O, MMIO или
   DMA-запросов; поздняя диагностика использует сохранённые счётчики.

Нет режима, где драйвер пытается продолжать DMA под неподтверждённым MMU
mapping. MAIR `0x44` даёт Normal-NC image и Device-nGnRnE PL011; TTBR0,
4-КиБ pages, 48-bit VA, ASID0, TTBR1 disabled. Барьеры и EL1 TLB invalidation
сопровождают смену roots, фактические регистры читаются обратно.

## Права, аппаратный вход и доверенный возврат

SAFE не имеет пользовательских leaves. USER сохраняет supervisor-only
замыкание образа ядра, таблиц, стеков, vectors и PL011. Kernel image mappings
остаются privileged RWX, UXN; системный W^X этим опытом не заявляется.

| USER VA | Назначение | EL0-права |
|---|---|---|
| `0x10000000..0x10001000` | Отдельная image-owned code page | RX, AP=3, PXN=1, UXN=0 |
| `0x11000000..0x11001000` | Свой стек | RW/NX, AP=1, PXN=1, UXN=1 |
| `0x12010000` | Ожидаемый адрес отказа | Отсутствует |

Фактические таблицы проверяются на полный набор user leaves и эффективные
права. Нет пользовательского alias ядра, storage/DMA буферов или таблиц.
Стек каждого запуска заново очищается, SP_EL0=`0x11001000`.

Каждый запуск — новый `ERET` в EL0t с entry PC=`0x10000000`, masked DAIF и
целочисленным X0. При X0=0 внешний код делает настоящее чтение отсутствующей
страницы: fault PC=`0x10000008`, FAR=`0x12010000`, ESR=`0x92000006` — Data
Abort lower EL, read translation fault level 2. Нижний synchronous vector 8
сохраняет X0..X30, SP_EL0, ELR/SPSR/ESR/FAR, TTBR0 и доверенный entry SP в
полный 320-байтный frame. Current-EL/kernel fault не становится user event.

После fault архитектурный путь включает SAFE, восстанавливает исходный
стек C-диспетчера и только затем сбрасывает active/context bookkeeping.
Guest подтверждает SAFE root, исходный dispatcher SP и отсутствие live
context до освобождения учёта фиксированного слота. Ошибочная инструкция
не возобновляется. Следующий свежий контекст получает X0=1 и **реально снова
входит в EL0 после fault**. Внешний код записывает маркер в X19, exit code в
X0 и исполняет `SVC #2` по offset 24. Ожидаются ESR=`0x56000002` и saved
ELR=`0x1000001c`. Интерфейс не принимает пользовательских указателей.

Возврат по штатному exit использует тот же SAFE/доверенный стек; повторно
проверяется освобождённый контекст. Неожиданный kernel exception остаётся
терминальной ранней диагностикой. Учёт одного конечного слота не является
общим allocator, scheduler или process ABI.

## Связь артефакта, диска и исполнения

`tools/test_disk_app.py` собирает boot image один раз и отдельно два payload
с разными marker/exit immediates. Вариант B помещается на новый диск; ELF,
raw Image и manifest перед VM должны оставаться побайтно теми же, что у A.
Третья свежая фикстура имеет валидное хранилище и негодный контейнер.

Проверка связывает команды/версии инструментов, SHA-256 ELF/Image/manifest,
отдельный ELF/raw code/контейнер payload, точные прочитанные байты и CRC,
загруженный диапазон и CRC code page, реальные PC/SP/root/syndrome, X19 и
exit code. Полные UART, команды QEMU, JSON и роли/хеши дисков сохраняются;
один UART PASS доказательством не является. Timeout/reset, ошибка ядра,
чужие PC/VA/origin, отсутствие read/drain, новый EL0-вход после отказа loader
или отсутствие свежего EL0-входа после fault дают FAIL.

Полный прежний набор, ARM64-only, storage runner T-P1.8A, воспроизводимость
и сравнение всех старых артефактов с точной базой, включая storage ELF/Image,
проверяются отдельно. Фактические счётчики берутся из отчёта. Android/Termux
T-P1.8B остаётся SKIPPED до собственного прогона владельца. Сообщённый
владельцем T-P1.8A 16/16 PASS, exit 0 на
`60c9a18fd6b3c23865d64ca5e544faf3a23c6bbf` — отдельный прежний результат:
два скриншота, все семь VM-фаз, без сырых UART/JSON и без версии QEMU в
успешных скриншотах. QEMU 11.1.3 виден лишь в предыдущей неудачной попытке,
остановившейся на host Python. Это не версия успешного T-P1.8A и не результат
T-P1.8B. VirtualBox и нативное оборудование остаются SKIPPED.
