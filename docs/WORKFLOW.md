# StyleOS — как продолжается работа

[Точка входа](PROJECT.md) · [Ветки](BRANCHES.md) · [Дорожная карта](ROADMAP.md)

1. **Идея.** Записываем её в [IDEAS](IDEAS.md), не выдавая за обещанную функцию.
2. **Решение.** Согласуем цель, альтернативы и границы. Фиксируем решение в [реестре](DECISIONS.md) или в отдельном техническом ADR. Подбираем готовые инструменты и зависимости, если они действительно уменьшают объём работы.
3. **Задание.** Указываем одну базу SHA, отдельную ветку, ожидаемый результат, неизменяемые части, условия остановки и критерий приёмки. Не размножаем параллельную работу без сверки refs. Технические правила — в [AGENTS.md](../AGENTS.md).
4. **Реализация.** В новой рабочей ветке README объясняет, что менялось и как проверить именно её. Не расширяем маленькую проверку до незапрошенной миграции ядра или ABI.
5. **Проверка.** Записываем SHA, инструмент и его версию, команду, входные образы, контрольные суммы при необходимости и фактические PASS / FAIL / SKIPPED. Результаты разных сред не объединяем. К отложенному результату явно добавляем причину. [Команды](TESTING.md) · [Папка отчётов](test-results/)
6. **Приёмка.** Владелец принимает результат в нужном контуре. Новое свидетельство сохраняем отдельно и обновляем [точку продолжения](PROJECT.md). Предыдущий отчёт остаётся с исходным срезом. Выпуск — отдельное решение.

## Минимум для README новой рабочей ветки

| Раздел | Что в нём должно быть |
|---|---|
| Назначение | Базовый SHA, цель, ответ на вопрос, чем ветка отличается от обычного образа. |
| Изменения | Затронутые области, что сознательно не сделано, связь с ADR. |
| Запуск и тесты | Воспроизводимые команды, нужные инструменты и ожидаемые признаки успеха. |
| Результаты | SHA испытанного кода, матрица по фактическим средам, ссылка на полные свидетельства. |
| Переход дальше | Что ещё не подтверждено и с чего продолжать. |

Исторические ветки не правим задним числом. Для них используется [центральный указатель](BRANCHES.md). Общую продуктовую информацию не размножаем по веткам. README ветки ссылается на реестр и фиксирует свой локальный срез.

## Ветки, история и релизы

- Документационные изменения публикуем отдельно от исходников. `docs/styleos-project` не означает перенос кода или переключение GitHub по умолчанию.
- Ничего не удаляем. Не переименовываем и не двигаем старые ссылки, не делаем force push. Историческую вершину можно дополнительно закрепить в `legacy/*` перед согласованным переходом ветки по умолчанию. Это добавление ссылки, не перенос файлов.
- При отдельном разрешении на переход сначала сверяем принятую кодовую базу, архивную ссылку и историю, затем меняем главную ветку согласованным способом. Не включаем в неё неподтверждённые профили только ради слова «актуальный».
- [Releases](https://github.com/LPYURA2/OS/releases) предназначены для одобренных сборок, привязанных к тегу и SHA. В описании выпуска указываем среду проверки, ограничения и контрольные суммы. Диагностический VDI, установочный образ и пакет системного обновления — не взаимозаменяемые вещи.
