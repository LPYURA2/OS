# Deep Drop v0 — восстановление обработчика на стенде

База — опубликованный первый рубеж `188d615191459f20c608472d63cbda88d81dcb9e`.
В тесте используется отдельный checkout SDK
`f1893b7ac932be2d079392e99094954c46029a08`. Общий код переноса, SDK, `main`
и загрузочные профили не менялись.

## Что доказывает тест

1. Родительский процесс хранит тестовый слайд. Рабочий процесс через два
   канала получает текст и вызывает исходную C-функцию «Презентаций» из SDK.
   Первый перенос успешно применён.
2. Во втором переносе исходник — реальный временный `.txt` с кириллицей и
   разными окончаниями строк. Дочерний процесс подтверждает получение всех
   байтов и ждёт разрешения на вызов SDK. Стенд посылает `SIGKILL` в этот момент.
3. Стенд получает EOF, подтверждает причину завершения через `waitpid` и
   автоматически запускает новый экземпляр обработчика. Новый PID и ответ
   `READY` проверяются до завершения неудачной операции. Родитель не
   перезапускается, содержимое слайда и исходного файла совпадает с прежним,
   а счётчик применений остаётся прежним. Неудачная операция не повторяется сама.
4. Явный повтор той же операции проходит через новый процесс. Счётчик
   увеличивается ровно на один, итоговый текст сравнивается побайтно,
   исходный `.txt` не меняется. Тест завершает и собирает новый процесс штатно.

Подготовка и применение результата идут через тот же `styleos_drop_transfer`,
что в первом рубеже. Процессы, каналы и наблюдение за завершением в этой
проверке предоставляет Linux. Это **не** проверка изоляции приложений,
системного супервизора, перезапуска оболочки, VirtualBox или нативного запуска
в гостевой StyleOS. Падение проверено при активном переносе, до ответа
обработчика. Сбои после применения результата и падение в простое не проверялись.

## Повтор проверки

Из корня ветки `feature/styleos-deep-drop-v0`, на Linux с C11-компилятором
и Python 3:

```sh
git fetch origin f1893b7ac932be2d079392e99094954c46029a08
git worktree add --detach ../styleos-sdk-fixture f1893b7ac932be2d079392e99094954c46029a08
python3 tools/test_deep_drop.py --sdk-dir ../styleos-sdk-fixture/sdk --recovery
```

Параметр `--recovery` запускает оба теста. Таймаут на исполнение каждого —
15 секунд. Тест не требует QEMU, сети после получения SDK или прав администратора.

| Проверка | Результат |
|---|---|
| Linux x86‑64, GCC 14.2.0, Clang 19.1.7 | 16/16 PASS каждым компилятором, из них 7 проверок контура восстановления |
| GCC с UndefinedBehaviorSanitizer | 16/16 PASS |
| 10 последовательных повторов полного стенда с GCC | 10/10 PASS |
| `python3 tools/test.py --all --output build/deep-drop-recovery-regression`, QEMU 10.0.13, Python 3.12.14 | 57/57 PASS |
| Обычные загрузочные артефакты x86‑64 и AArch64 | 4/4 побайтно совпали со сборкой `main` на `9327131` |
| Гостевой Deep Drop, VirtualBox и Termux | Не запускались на этом этапе |

Следующий шаг для проверки уже в ОС — подключить перенос и супервизор к
гостевой оболочке и запустить «Презентации» в госте. Порядок описан в
[дорожной карте](../../ROADMAP.md).
