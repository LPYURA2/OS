# StyleOS — порядок работ после приёмки ядра

Решение владельца от 25.11.2026. Это план будущих работ, не отчёт о готовности.
Текущий технический кандидат: S855 8c2ca6453e2d7772698eebbcdf276cbdbd964e45; S854 принят.
Обязательные шесть рубежей фундамента и KFA-01..12 остаются без изменений.
До их закрытия пользовательские этапы не начинать. После комплексной приёмки
обсудить производительность, технический уровень и требования; оптимизацию
курсора выполнять отдельно без изменения остального интерфейса.

## Очередность

1. **Процессы.** Довести реальный kernel-owned реестр, учёт CPU/памяти,
   жизненный цикл, снимки и защищённое завершение. Вкладки «Процессы»,
   «Производительность», «Подробности»; приложения, фоновые и системные
   процессы, реальные PID/PPID, статусы, поиск и сортировка. Не подменять
   процессы окнами/сеансами, не рисовать фиктивные проценты CPU.
   Критические системные задачи защищены. Переиспользовать
   [существующую модель](architecture/PROCESS_MANAGER_WINDOWS_BEHAVIOR.md).
   Полностью независимый Processes.tea завершить на этапе приложений,
   не нарушая зависимость от файловой системы и загрузчика .tea.
2. **Файловая система.** Файлы, каталоги, тома, права, устойчивое сохранение,
   восстановление, обновление без потери данных. Переиспользовать проверенные
   компоненты StyleFS, не заменять формат без отдельного решения.
   Раздельные системный носитель и постоянный диск данных.
3. **Полностью независимые приложения.** Родные .tea в собственных
   пользовательских процессах/адресных пространствах, проверяемый загрузчик,
   IPC и системные сервисы окон/файлов, доступ только по выданным правам.
   Сбой или закрытие одного приложения не обрушает оболочку и соседние
   приложения. Завершить Processes.tea и Проводник по утверждённым макетам.
   Предустановленные приложения также .tea; не имитировать независимость
   списком окон. Внешний пакет SDK должен устанавливаться и запускаться
   без пересборки ядра. Порядок отдельных приложений уточняется по зависимостям.
4. **Экраны приветствия, входа, выбора пользователя и блокировки.**
   Реальные учётные записи, аутентификация и kernel-owned сеансы, блокировка,
   выход, создание пользователя; изоляция данных и прав между пользователями.
   Следовать [утверждённым макетам](design/APPROVED_UI_REFERENCES.md).
   Не встраивать демонстрационные имя, пароль или время.
5. **Проверка в VirtualBox.** После перечисленных этапов отдельная испытательная
   ВМ x86-64 UEFI, штатный загрузочный ISO и постоянный диск данных; проверка
   загрузки, процессов, сохранения/повторного открытия после перезапуска,
   независимых приложений, пользовательских сеансов, Deep Drop и внешнего
   вида. Проверку установки/обновления проводить на копии образов, не
   перезаписывать старый VDI. Готовность установщика и конкретные параметры
   виртуального железа требуют отдельного подтверждения; не выводить PASS
   VirtualBox из QEMU. Физические ПК и ARM64 — отдельные профили.

## Deep Drop — обязательная сквозная функция, не отложенный бонус

Сохранить существующую концепцию переноса выбранного объекта и
самовосстановления. На этапе файловой системы — ограниченный доступ к
выбранному объекту, исходник сохраняется при отмене/ошибке. На этапе
независимых приложений — системный механизм обмена объектами через IPC;
передача текста, файлов и изображений между отдельными процессами, в том
числе свёрнутыми окнами; «Создать заметку» из выделения, заметка/текст в
презентацию, фотография между приложениями. Конкретные типы и форматы
расширять по готовности получателей. Не давать всему приложению доступ к
каталогу лишь из-за передачи одного файла. Отмена, сбой обработчика,
перезапуск только обработчика, повтор без двойной вставки, сохранность
источника, доступность оболочки и других приложений — обязательные
сценарии. Проверить изоляцию между пользовательскими сеансами после этапа 4.
В VirtualBox повторить сквозные сценарии. Перезагрузка всей VM не является
восстановлением Deep Drop. Подробности исходной приёмки в ROADMAP.md.

## Правила

Интерфейс строго по утверждённым макетам. Текущую палитру и рабочий стол
сохранить. Не вводить новые макеты без согласования, не копировать Windows
визуально. Никаких пустых кнопок и ложных демонстрационных показателей.
Каждый этап — отдельная ветка, исходники, сборка, фактические испытания,
точка продолжения и сообщение для нового чата. Main и принятые refs
сохранять. Этот документ подготовлен на отдельной docs-ветке, переносить
его и актуализированные ссылки в следующий технический этап от принятой
базы, не подменяя текущий SHA и не запуская повторный CI ради документации.
