# StyleOS — дополнительные требования владельца

Утверждено владельцем 25.11.2026. Требования к будущему продукту, а не заявление о готовности функций. Они дополняют предыдущие решения и не отменяют ограничения текущего технического этапа.

## Приоритет
Сначала завершить этап 863 (штатная интеграция ядра), затем 864 (комплексные нагрузочные испытания и стабильность), 865 (полная приёмка KFA-01–12 и закрытие шести обязательных рубежей). Только после реальной комплексной приёмки — Style Kernel 1.0. После неё оценить технический уровень, оптимизацию, производительность и системные требования. Остальные требования сохранять и учитывать в архитектурных решениях, но не начинать их реализацию вместо завершения ядра. Порядок последующих работ — [POST_KERNEL_ROADMAP.md](POST_KERNEL_ROADMAP.md).

## Интерфейс
- Строго придерживаться утверждённых макетов из библиотеки проекта. Сверяться с [реестром утверждённых макетов](design/APPROVED_UI_REFERENCES.md), при отсутствии оригинала не придумывать замену без согласования.
- Сохранить существующий рабочий стол, его функции и собственный стиль.
- Тёмная тема по умолчанию.
- Не копировать Windows или Linux, использовать удачные принципы удобства.
- Плавная работа курсора без полной перерисовки экрана.
- Возможность переноса панели задач.

## Deep Drop
- Обязательная сквозная системная функция передачи выбранных файлов и данных между приложениями, а не самостоятельное приложение, буфер обмена или общее восстановление системы.
- Перетаскивание выбранного текста, изображений, файлов и других поддерживаемых объектов, в том числе в свёрнутые приложения. Получатель определяет место и способ вставки/открытия объекта.
- Сценарии владельца: фото Instagram → Telegram; текст браузера → Документы; выделить текст в Документах → «Создать заметку» (файл заметки рядом с сохранённым документом); перетащить файл заметки из Проводника → Презентации, где открывается/импортируется её текст. Ранее также утверждался перенос из Telegram в Instagram/ВКонтакте.
- Для сторонних приложений, в том числе будущих Android/Windows-подсистем, сохранять единый пользовательский сценарий; передача зависит от реально поддерживаемых форматов и разрешённых получателем/источником интерфейсов. Не обходить ограничения доступа или защиту чужого приложения.
- Передавать только выбранный объект, не весь каталог. Исходник сохранять при отмене/сбое. Отказ не должен приводить к скрытой отправке или двойной вставке.
- При сбое Deep Drop уведомление показывает причину/код ошибки, состояние службы и результат перезапуска; перезапускать именно службу Deep Drop, при необходимости по кнопке. Незавершённый перенос отменяется. Не перезагружать систему для восстановления службы.
- «Восстановление» — отдельный общий механизм восстановления системы и функций, не определение Deep Drop. Изоляция приложений/сеансов, сохранность данных и восстановление обработчика остаются обязательными условиями.
- Не начинать новую реализацию Deep Drop вместо завершения ядра; сохранить существующие наработки. Подтвердить сквозные сценарии после появления независимых приложений и соответствующих подсистем совместимости.

## Встроенные приложения
Параметры, Документы, Таблицы, Презентации, Заметки, Текстовый редактор, Проводник, Браузер, Процессы.
Все родные приложения используют формат .tea, работают независимо от оболочки и друг друга. Независимость должна обеспечиваться реальными процессами и изоляцией, а не внешним видом окон.

## Системные возможности
- Собственная полноценная файловая система.
- Поддержка распространённых форматов документов.
- Реальный диспетчер процессов с потреблением ресурсов.
- Приветствие, вход, выбор пользователя и блокировка.
- Установка и обновление системы через ISO.
- Обновление из файла с безопасным откатом.
- SDK для сторонних разработчиков.
- Магазин приложений App World.
- Сеть, интернет и системная поддержка VPN.

## Перспективы
- Системная совместимость с Android и Windows-приложениями без отдельных пользовательских эмуляторов.
- Поддержка Intel, AMD и ARM64 с отдельными испытаниями. Результат одной архитектуры, CPU, QEMU или VirtualBox не заменяет испытания другой платформы.
- Мобильная версия и переключение на настольный интерфейс при подключении монитора.
- Безопасность, производительность и умеренные системные требования.

## Принципы разработки
Не изобретать заново готовые качественные решения без необходимости. Не удалять предыдущие наработки. Не подменять реальные функции заглушками. Сохранять исходники, сборки, документацию и контрольные точки. Каждый технический этап — отдельная ветка от принятой базы, реальные испытания и честная фиксация PASS/FAIL/SKIPPED; main и принятые refs не менять без разрешения. Отчёты короткие, объём испытаний и работы не сокращать.
