# StyleOS — восстановление полноценной 730 из исходной 709

Дата фиксации: 2026-11-21. Эта ветка создана **строго от** восстановленного исходного коммита Build 709: `f81631d980824f2338ae68eaca0a7c549cc8161f`. История, `main`, исходная ветка 709, оригинальные 730/744 и пользовательские VDI неприкосновенны.

## Эталоны и происхождение сведений

- **S709** — исходное дерево GitHub `restore/styleos-source-705-to-709` (SHA выше); независимый ZIP исходников `StyleOS-709-Full-Source.zip`, SHA-256 `af935a237c05b49aa1fe79d874f279fd155a87dcba418c07f8d39fa249205252`. GitHub Actions `44844146004` (отдельная CI-ветка, `76e45c2`) успешно собрал EFI/ISO, прошёл host и QEMU Desktop v0. На локально распакованном дереве 709 повторно подтверждена компиляция PE32+ `BOOTX64.EFI` и 10/10 host-проверок. Это не означает побайтовую идентичность исторической Build 709 или тест VirtualBox.
- **B730** — **оригинальный** `StyleOS-730-Test.zip`, SHA-256 `ae9641da573bc8618dcde06b6effa30fb058adae35a7e00df4a2cafd1f407`. Внутри: `START.txt`, `StyleOS-Install-x64.iso` (SHA-256 `175db7b0d8ec777a2b2da0c69b3b41b94ac5e837f49a7da25dcb49243da7ce91`), `StyleOS-Data-2.vdi` (SHA-256 `3006f192abc714d51b67f29ca9b67410af88f8ebf95c236066d4adab12142c9f`), `Installer-Preview.png`, `SHA256SUMS.txt`. Отсутствуют исходные C/ASM файлы. Архив и контрольные суммы просмотрены без изменения. Инструкция утверждает проверки QEMU, но в рамках этого этапа оригинальная 730 **повторно в VM не запускалась**.
- **B744** — оригинальный `StyleOS-744-Documents-Intermediate.zip` (SHA-256 `22e87caca314d43bd8832fe35b8838dc18179105e32c59a204e3e18d43c825af`): отдельный эталон будущей функциональности Documents, **не** исходники 730.

Её можно изучать и аккуратно переносить проверенные решения в новую ветку, **но не объявлять оригинальным исходным кодом 730**.
- **Documents 751–758** — отдельная экспериментальная линия, не сливать целиком с ядром/рабочим столом 709/730. `Documents.tea` до 758 не подтверждён как штатно запущенный гостевой модуль.

## Функциональный контракт оригинальной 730

Статусы: «709 есть» означает обнаруженный в исходниках 709 механизм, а не полное совпадение поведения; «730 заявлено» означает прямой сценарий из оригинального `START.txt` и/или бинарный признак, требующий теста. «Не доказано» означает отсутствие сквозного гостевого доказательства нового исходного кода.

| Узел | Что известно о 709 | Контракт 730 / источник | Разрыв и критерий проверки |
|---|---|---|---|
| Загрузка | `efi_main` → `kernel_main` → `desktop_v0_run`, реальный EFI/ISO | Установочный ISO x86-64 для новой VM с EFI, 1 CPU, 512 MiB, PS/2 | Оставить работающий путь запуска и проверить обе формы: установщик и установленный системный VDI |
| Графический установщик | В восстановленной 709 отсутствует отдельный графический сценарий установщика 730 | 8 GiB пустой VDI как IDE Primary 0; ISO как IDE Secondary 0; выбор диска и **второе подтверждение**; снимок показывает 8 GiB «Готов к установке» и 32 MiB «Защищён от записи установщиком» | Диск установщика не писать; отказ для неподходящего/неподтверждённого диска; чистая установка, затем boot без ISO |
| Рабочий стол и окна | `kernel/desktop_shell.c`, framebuffer, PS/2, окна, drag, переключение, repaint | F10 пересоздаёт оболочку; геометрия окон сбрасывается, редактор остаётся | Отделить runtime приложений от окон; F10 не пишет на диск и не уничтожает черновики |
| Проводник | F2, `desktop_stylefs.c`, перемещение, копия файлов, операции на одном томе | F2 открывает Проводник; «Мой компьютер» показывает «Данные 1» и «Данные 2» | Реальные тома, не фиктивные элементы; проверка обоих томов и перезагрузки |
| Редактор | F3, UTF-8 черновик в глобальном состоянии оболочки, Ctrl+S, 64 KiB стиль данных | F3 → несохранённый текст → F10 → Ctrl+S → reboot → open | Сохранить текст, dirty/caret и правильный файл через F10; запись/открытие проверять на реальном VDI |
| Заметки | В 709 `NOTES` фактически переименовывается в «Текстовый редактор»; независимого окна заметок нет | F5 открывает «Заметки» одновременно с редактором | Отдельные черновики/состояние, разные файлы, никаких смешиваний; F5 из R730-F5 проверен в QEMU как **новая** реализация |
| Процессы | В 709 `TASKS` — окно списка окон, а не доказательство независимых процессов | F8 отображает PID, после F10 PID приложений сохраняются | Проверить уникальность/устойчивость идентификаторов; не путать реестр сеансов с CPL3/изоляцией адресных пространств |
| Второй диск | 709 использует один активный диск данных; StyleFS v1/v2, отдельный системный профиль обновления | `StyleOS-Data-2.vdi` после установки подключается вместо ISO; «Данные 2» содержат папку «Проба» с файлом 20 MiB | Поддержка двух отдельных data-томов без потери/переформатирования первого; физические IDE-порты и монтирование проверить |
| Фоновое копирование | В 709 `sfs_copy` вызывается синхронно, папки не копируются (`Копирование папок пока недоступно`) | Ctrl+C папка «Проба» на «Данные 2», Ctrl+V в папку «Данные 1», продолжение редактирования во время копирования | Очередь/конечный автомат с ограниченным временем одного шага, прогресс, целостность 20 MiB, повторная попытка |
| Отмена копирования | Отдельной фоновой операции в 709 нет | Esc или кнопка «Отменить» прерывают операцию; во время копирования том назначения допускает чтение, но блокирует иную запись | Очистка незавершённой целевой операции, читаемость данных, отсутствие частично видимого готового файла |
| Межтомовое перемещение | В 709 только внутренняя операция `sfs_move` | В 730 **Ctrl+X между томами не поддерживается** | Явный корректный отказ, без удаления исходника |
| Обновления и откат | Подписанный локальный `.supdate`, A/B-слоты, CRC и readback в специальном профиле 709 | Не описаны отдельным приёмочным шагом оригинального `START.txt`; должны не регрессировать при восстановлении | Сохранить проверки подписи, fallback и независимость данных, не подменять реальный secure boot |
| Deep Drop | В 709 есть локальная передача текста из Проводника в редактор | Полный межпроцессный Deep Drop **не доказан по START.txt 730** | Сохранить 709-работу; отдельная приёмка ограниченного доступа/аварийного восстановления после реального IPC |
| Приложения | В 709 функциональность редактора встроена в shell | В бинарном 730 встречаются `Documents.sapp`, `Editor.sapp`, `Notes.sapp`, `Explorer.sapp`; это ещё не доказательство отдельных процессов | Для будущей системы **единственный native формат .tea**; .sapp — только историческая подсказка, без восстановления как стандарта |
| Безопасность | Тестовая изоляция EL0/CPL3 в отдельных профилях, не полноценный desktop process loader | В оригинальной 730 PID и оболочка по описанию автора, изоляция каждого приложения аппаратно НЕ подтверждена | Новая система должна иметь отдельные адресные пространства/права; host-реестр не считать процессами |
| VirtualBox и железо | Отдельная проверка требуется | Оригинальный `START.txt` прямо говорит, что 730 испытывалась в QEMU, **не** VirtualBox и **не** физическом ПК | В отчётах помечать NOT RUN, не переводить QEMU PASS в VirtualBox PASS |

## Принятый порядок восстановления

**Шаг A — сохранить источник истины.** Новая ветка строго от SHA 709. CI на каждом push должен собирать EFI/ISO, запускать host и QEMU, архивировать ПОЛНОЕ дерево исходников этого SHA вместе с проверочными файлами. Ошибки host/QEMU не маскируются `continue-on-error`. Публикация CI-артефакта не заменяет независимый постоянный бэкап (артефакты имеют срок хранения).

**Шаг B — восстановить поведение F2/F3/F5/F8/F10.** Изучить патчи R730-F5 и переносить небольшими самостоятельными коммитами, не сливая ветку целиком. Сначала раздельный editor/notes state и F10, затем реестр сеансов и QEMU сценарии. При этом текущие PID считать только реестром, пока не появится настоящий процессный loader.

**Шаг C — восстановить дисковую модель 730.** Установщик на новый 8-GiB VDI, защита установочного носителя, установленный boot, два StyleFS v2 тома, работа с настоящими файлами; затем фоновые межтомовые copy/cancel с прогрессом. Не менять пользовательский образ эталонной 730.

**Шаг D — системные приложения.** Определить версионированный native ABI, реальные процессы/окна и file broker; `.tea` по утверждённому формату, встроенность — только предустановка, не код приложения в ядре/оболочке.

**Шаг E — документы и поздние функции.** Лишь после воспроизведения поведения 730 переносить проверенные узлы 744 и 751–758, с визуальной сверкой всех 14 макетов и настоящим запуском `Documents.tea` в госте. Потом Презентации, Таблицы, остальные окна и Deep Drop.

## Инварианты

- Никогда не изменять `main`, `restore/styleos-source-705-to-709`, оригинальные 730/744 ISO и VDI, а также `Portable-os`.
- Не делать `push --force`, не переобозначать восстановленную экспериментальную ISO как исходную 730.
- В отчёте каждого этапа: точный SHA, исходная ветка, changed files, реальная команда, окружение, PASS/FAIL/NOT RUN, SHA256 EFI/ISO/исходников, условия приёмки.
- Сохранять работающий рабочий стол, язык RU/EN, StyleFS v2, обычные файлы, обновление и откат. Новые интерфейсы сверять с утверждёнными макетами, не заменяя их упрощённым UI.
- Проверка исходного 730 `START.txt` и бинарного PE не равна независимому тестированию 730; неизвестные возможности не придумывать.
