# 778 — ядровая граница отображений (read-only closure audit)

## Зачем

После 777 корни SAFE / User A / User B создаются лишь с **одной**
диагностической supervisor-страницей. Попытка использовать их как рабочие
`CR3` приведёт к отсутствующим отображениям кода, стека и обработчиков.
**Ни одна строка этого этапа не переключает CR3 на корни 777.**

## Реализовано

- В `kernel_closure_audit` формализована обязательная проверка семи
  одностраничных ролей: code RX; exception code RX; data RW/NX;
  kernel stack RW/NX; GDT RW/NX (возможен аппаратный Accessed-бит);
  IDT RO/NX; TSS RW/NX.
- Во всех трёх корнях идентичные роли должны быть supervisor-only,
  разрешения совпадать и физическая страница должна совпасть с заранее
  заявленной. Попытки алиасинга, подмены физического адреса, mapping с
  U-битом, RWX, отсутствующая роль или не подтверждённая attestation
  отклоняются **до** разрешения какой-либо активации.
- `DVM_KERNEL_MAX_SPANS` увеличен с 4 до 8 для поддержки ограниченного
  набора ролей. Вместимость таблиц (72 страницы на три корня) не изменена;
  прежний конструктор остаётся транзакционным и никогда не пишет CR3.
- В аппаратном профиле QEMU проверяется, что у существующего корня 777
  отсутствует нужная роль, и появляется маркер отказа. Валидатор UART
  требует маркер и проверяет его единственность.

## Доказательства и ограничения

Host ASAN/UBSAN и COFF проверяют положительный **синтетический** набор
из семи ролей и отрицательные случаи. Это проверка архитектурного
контракта, а не физических адресов UEFI. В QEMU подтверждается только
отказ неполному корню 777 и прежний действующий аппаратный roundtrip;
новый корень **не активируется**.

`KCA_OK` означает только структурную полноту перечисленных семи
страниц и успех callback. Это **не** гарантия полной безопасности
переключения `CR3`: отсутствует полный обход всех страниц PE-образа,
динамических стеков/IST, адресов GDT/TSS/IDT по регистрам процессора,
firmware runtime, serial/портового I/O, GOP frame buffer / MMIO,
PAT/cache policy, DMA, нескольких CPU и fail-safe обработчиков.

**Следующий шаг (779):** получить у архитектурного слоя реальное
инвентарное доказательство всех зависимостей kernel/device context
с проверкой cache policy/потока прерываний. Только затем строить полный
корень, проводить отдельный `CR3` switch/restore в QEMU и не использовать
его в обычном Desktop до аппаратной приёмки.

## Сохранность продукта

`main` и принятые ветки не изменять. Приложения `.tea` в обычном Desktop
пока не запускаются в собственных CPL3-контекстах. Полного установщика
`.tea` нет (есть host-staging и UI). После завершения независимых
приложений — экран входа по утверждённому макету, система пользователей,
StyleFS и финализация Проводника по макетам.
