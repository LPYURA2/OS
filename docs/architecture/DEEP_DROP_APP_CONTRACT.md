# Deep Drop — common application contract and SDK requirement
Status: owner requirement (28 November 2026); implementation of the generalized contract is deferred until real independent applications exist. This is not an implemented ABI or finalized manifest schema.
 
## Product requirement
Deep Drop must be a system capability available to new native .tea applications, including third-party packages installed after the OS has shipped. No recompilation of kernel/shell, hard-coded app name, per-app shell modification, or privileged application is required for ordinary integration. The same public SDK contract is used by preinstalled and newly installed applications. An application may implement source, receiver, or both, depending on its legitimate functionality; compatible data types and explicit permissions are required. Do not promise arbitrary insertion into a program that has no receiver implementation. Unsupported targets must refuse predictably without crashing or silently changing data.
 
## Architecture requirements for the next app stages
- The system service owns transfer lifetime, authority, cancellation and cleanup; compositor owns pointer capture, taskbar activation, destination feedback and trusted gesture creation. App owns its selection, supported input types, rendering, insertion, undo/draft semantics and persistence.
- Provide a versioned SDK wrapper over authenticated process IPC, with runtime capability discovery (source/receiver, supported types and version). Names below are conceptual, not frozen ABI. Manifest declarations are descriptive, never sufficient to grant data or filesystem rights. No hard-coded product identities in routing.
- First contract: bounded UTF-8 text COPY, explicit selection/request, offer, consent, read once, finish or cancel. Existing 72–74 reference wire stays compatible until a deliberate versioned ABI decision. A successful finish acknowledges transfer, not durable document save. Unknown versions/types, denied permissions, missing endpoints, timeouts and pressure fail closed with no leaked buffer or repeated insertion.
- A new app's launch and live window are registered through the normal .tea runtime; identity must be PID/generation/root/window and active session, not display name or task index. Minimized targets may be restored only by trusted UI. Do not expose raw pointers or allow an app to authorize a transfer to itself.
- New types after real apps: typed content negotiation, bounded metadata, scoped StyleFS revision/read grants and streaming for files including large files, images and office objects. Avoid copying entire file into memory, automatic persistence, unrequested network export or destructive MOVE. Revoke grants on cancel, fault, session change and timeout. Separate service recovery from unsaved document recovery. Compatibility layers (WinStyle/Android) are separate integration boundaries, not already supported.
- Ship SDK documentation, simple sender/receiver examples and conformance tests. A new independently developed package built against public SDK must be installable and able to exchange supported content with a preinstalled app without changing the shell/kernel binary. Test both directions, minimized receiver, explicit consent, cancellation, stale/faulted endpoint, incompatible type, permission denial and resource cleanup. Test unsupported app safely. Prove actual guest process isolation and disk/memory effects. The current pinned acceptance clients do NOT satisfy generic installation or production SDK conformance.
 
## Delivery order
1. Close the bounded 74 text base and retain evidence.
2. Build real independent applications and their shared native runtime/SDK; design their selection and insertion interfaces so Deep Drop can be integrated without rewriting the UI.
3. Return to Deep Drop: implement the public extensible contract and supported data types across the system, then prove interoperability with a newly installed independent .tea app. Extend coverage incrementally; no special-case shell integration for each future app.
 
Keep approved interface mockups, optimization and prior accepted revisions. Generic installer/trust, versioned application ABI and file types remain work to implement; no promise that every legacy/foreign app already supports Deep Drop.
