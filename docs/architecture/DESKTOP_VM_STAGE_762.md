# StyleOS 762 — подготовка собственных таблиц страниц (x86-64)

База: принятая 761, `70341fe1d1424053955439b9f3bc9e814495ec25`.
Ветка: `feature/styleos-owned-vm-stage-762`.

## Суть изменения

Новый `kernel/desktop_vm_stage.c` и `include/styleos/desktop_vm_stage.h`
создают **неактивный кандидат** таблиц страниц: 3 корня x86-64, 4 уровня,
только 4-КиБ листья. Корень 0 (SAFE) содержит исключительно переданные
владельцем памяти supervisor-карты. Корни 1 и 2 содержат те же supervisor-
страницы и **только собственные** user-код RX, user-стек RW/NX и user-данные
RW/NX. Физические страницы двух пользователей должны быть различными;
одинаковые виртуальные адреса разных пространств допустимы. Поиск проходит
через самостоятельно построенные реальные PTE, а не ожидаемую таблицу прав.

Конструктор отклоняет пересекающиеся VA/PA, W+X, смешение kernel/user,
невыравнивание, неизвестные биты прав, неканонические/выходящие за пределы
адреса, вложение пользовательских физических страниц в адреса таблиц,
отсутствие ёмкости. При **любом отказе** полностью обнуляет кандидатные
таблицы и выходные корни. Результат доступен только в коде ядра;
пользовательских указателей, ioctl и syscall не добавлено.

Физический базовый адрес массива таблиц поступает **из отдельного доверенного
источника будущего менеджера памяти**. Он никогда не выводится простым
приведением C-указателя. Адреса отдельных страниц также задаются только
доверенным владельцем памяти. Сам конструктор **не удостоверяет** их
физическое владение или физическую доступность и не делает их активными.

## Чего нет и почему

- В обычном desktop по-прежнему активен **UEFI-наследованный CR3**. Тестовые
  массивы из host-кейса не становятся настоящей памятью гостя. Ни один
  `mov %cr3` и ни один реальный вход в CPL3 не добавлен в этот этап.
- Таблицы нельзя применять до полной проверки live kernel image, стека,
  GDT/TSS, IDT, UART, таймеров, framebuffer, MMIO, BIOS/UEFI зависимостей,
  физического владения страниц и NXE/4-level CPU mode. Отдельные RX/RW
  сегменты в host-кейсе **не подтверждают** фактическую W^X-разметку PE.
- Нет общего PMM, безопасного копирования адресов пользователя, syscall,
  таймера/вытеснения, сигналов, счётчика реального CPU/RAM, .tea-лоадера,
  работающего `Processes.tea` и механизма завершения критических задач.
- Массив таблиц ограничен 24 страницами на корень. Это **не** универсальный
  менеджер виртуальной памяти, не поддерживает 5-level или huge pages,
  high-half mappings и произвольные устройства.

## Проверка и точка приёмки

```sh
python3 tools/test_desktop_vm_stage.py --output build/desktop-vm-stage-host
python3 tools/build.py --arch x86_64 --desktop-v0 --output build/desktop-vm-stage-efi
```

Host ASAN/UBSAN проверяет положительные права страниц, изоляцию адресов,
разные PA при одинаковой VA, границы, отрицательные кейсы, отсутствие
частично опубликованных корней и повреждённые указатели промежуточных
таблиц. Компиляция COFF подтверждает соответствие профилю UEFI.

Полный CI этапа проверяет прежний GUI/диск/тесты обычного рабочего стола в
QEMU и **отдельный экспериментальный CPL3/EL0 профиль 760**, который не
зависит от нового конструктора. Это важно: PASS прежнего CPL3 не доказывает,
что новые таблицы были активированы аппаратно. Итог CI смотреть по SHA ветки.

### Следующий инженерный этап

Создать *доказанное* хранилище таблиц, полученное из реального boot memory
и подтверждённое старым read-only UEFI walk. Закрыть всё необходимое для
перехода CR3 и возврата (TSS/IDT/стек, активные устройства, cache и NXE),
затем провести **отдельный контролируемый QEMU-тест** переключения в CPL3
из обычного desktop без запуска пользовательских `.tea`. После него — .tea
loader, настоящий PID и право на процессные снимки через syscall.

Принцип: новые root-планировщики не рисуют проценты CPU и не превращают
сеансы рабочего стола в фиктивные PID. Дизайн рабочего стола и формат `.tea`
не изменяются.
