# StyleFS — контракт с Style Kernel 0.1 (проект реализации)

Это спецификация следующей файловой подсистемы, а не утверждение о её реализации. Основа 4c52818f7d36c29007b1b47d46ee7666d4c552bb; ядро 0.1: 371ef59f4419955dd4a63de820e8eea1391495bb. Сначала завершить необходимую проверку Processes. Не менять дисковый формат StyleFS v1/v2 или утверждённый интерфейс без согласования.

## Что уже есть в исходниках
- include/styleos/stylefs.h, kernel/stylefs.c: синхронный sfs_io read/write/flush для 512-байтных секторов, mount без записи, явный host-only форматтер, два банка метаданных, CRC, поколение, caller-owned workspace. Для v2 CRC содержимого проверяется при чтении, не сканированием всего диска при mount.
- kernel/desktop_volume_io.c: проверка размера и смещения отображаемого тома; ограниченные callbacks; read-only без write/flush. Не обнаружение дисков и не kernel-owned менеджер томов.
- include/styleos/ata_runtime_863.h: узкий QEMU PIO secondary-master, проверяемые порты, sticky quarantine, конечные опросы, без автоматического повтора. Не универсальный драйвер.
- StyleFS v2: 256 записей (включая корень), 32 МиБ–1 ГиБ том, максимум 64 МиБ файл. Реальная интеграция с разрешениями, приложениями и произвольными томами не завершена.
- sfs_copy_job_step: пошаговое копирование данных в неопубликованный extent, CRC, flush, metadata commit, контроль поколений. Финальная фиксация метаданных выполняет дополнительные I/O; max_sectors не является доказанным лимитом всех физических операций финального шага.

## Предлагаемые границы
1. Kernel-owned block service: зарегистрированный проверенный носитель, идентификатор + поколение подключения, размер/границы секторов, отдельные права read/write/flush. Различать системный ISO (read-only) и диск данных. Запрет прямого ATA/MMIO/DMA из приложений; никаких новых аппаратных грантов. Отсоединение аннулирует старые handles; неизвестный/пустой носитель не форматировать. Не считать ATA serial криптографической идентичностью.
2. Владение буферами: перед записью скопировать валидированные пользовательские данные в ограниченный kernel-owned буфер; читать в staging, публиковать только после проверки результата и CRC соответствующего файла. Проверять диапазоны, права, overflow, срок жизни, принадлежность процессу и поколение тома. Не принимать user callbacks/адреса устройств. Операция хранит свои буферы до завершения/отмены; смерть процесса не освобождает ещё используемый буфер. Никакой general RAM grant. Один сериализованный writer/workspace на том; исключить повторный вход. Дальнейший async API отдельно после проверки.
3. File service: непрозрачный handle + generation и привязка к процессу/правам/тому, не сырые указатели и не один переиспользуемый индекс записи. Методы list/stat/open/read/write/create/mkdir/rename/remove/close; проверка прав до I/O. Правила владения и ACL сначала определить, затем реализовать; текущий sfs_entry не содержит полноценного ACL. Границы на имя/размер/путь, честные ошибки и отсутствие утечек.
4. Сохранность: сохранить действующую схему payload -> flush -> inactive metadata -> flush -> commit header -> flush. Не подтверждать сохранение до успешного последнего flush. Неопределённый результат записи/flush переводит том в состояние recovery-required, запрещает новые мутации до проверенного remount. При неопределённом commit не обещать старую версию и не повторять мутацию вслепую; после remount проверить поколение/CRC и фактическое состояние. Не удалять исходник cross-volume move до подтверждения назначения. Не обещать сохранность при неисправном устройстве, лгущем о flush.
5. Отказы и изоляция: ошибка носителя, повреждённая запись, неверный указатель, завершение процесса в ходе операции — отказ конкретной операции, а не всей системы, кроме уже документированных kernel-invariant fail-stop. Не выдавать частичный результат как успешный файл. Отдельные ошибки invalid/denied/stale/not-found/full/io/corrupt/uncertain/cancelled. Связать существующие SFS_* коды с новым API; не менять их тихо.
6. Независимые приложения и Deep Drop: scoped capability на выбранный файл/поток, не на весь каталог. Исходник сохраняется при сбое/отмене. Передача через IPC, уникальный ID операции, проверка завершения и запрет двойной вставки. Сбой обработчика — отмена незавершённой операции, перезапуск только службы и сохранение остальных процессов/оболочки. Никакой перезагрузки системы вместо восстановления службы. Разрешения между пользователями проверяются после появления реальных сеансов.

## Обязательная проверка до принятия интеграции
- Host: границы секторов и arithmetic overflow, read-only, stale handle после remount и reuse, invalid user span, cross-process denial, concurrent workspace refusal, все позиции fault injection read/write/flush, payload CRC, повреждение банков, заполнение, поколение, отмена. Отдельно модель и реальный guest.
- Guest: штатный ISO и независимый постоянный диск, перечисление действительных томов, создание/чтение/изменение файлов и каталогов; холодное сохранение/повторное открытие. Два тома; отказ чужой идентичности; никаких записей на системный ISO или неизвестный носитель.
- Guest recovery: разрыв операции на отдельных границах write/flush/commit на одноразовой копии диска; после remount целая подтверждённая версия либо явно диагностированная ошибка, не ложный успех. При I/O ошибке соседний процесс продолжает работу; при завершении владельца буфер не отдаётся преждевременно. Сравнение исходника и назначения после неудачного копирования.
- Regression: обычный Desktop, реальный CPL3, scheduler, forced stop/fault, исторические профили; сырые логи и хеши, независимая проверка по возможности. Не засчитывать модель как физический диск. VirtualBox/физическое оборудование — отдельные испытания.

Этап проектирования не меняет код, права, формат или интерфейс. Следующий технический этап Processes 02: фактический гостевой вызов snapshot, реальный PID/state/учёт, затем безопасное окно управления. После Processes — реализация и тесты описанного контракта по отдельным веткам.
