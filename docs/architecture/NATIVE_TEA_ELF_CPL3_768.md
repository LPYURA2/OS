# StyleOS 768: реальный ELF64 из проверенного .tea в аппаратном CPL3

База: принятый этап 767, `07c9ebd2b4637eca9e5cbc5a837690ed0501a371`.
Ветка этого этапа: `feature/styleos-native-tea-cpl3-768`.

## Выполнено

1. Внешний к ядру исходник `apps/tea_768_minimal.S` собирается **отдельно**
   в ELF64 ET_EXEC по `apps/tea_768.ld`, с фиксированным entry `0x10000000`.
   Он не линкуется в PE-образ; далее canonical `.tea` v1 упаковывается
   существующим `tea_package.py`. `build_native_tea_768.py` проверяет пакет,
   извлекает ELF, подтверждает SHA-256, адреса пяти символов, затем генерирует
   временный `.h` с *байтами ELF*, а не бинарный Git-исходник.
2. `kernel/native_tea_elf.c` независимо проверяет ELF64/x86-64, ET_EXEC,
   одну RX-PT_LOAD страницу, полный размер/вход/границы, W^X и SHA-256,
   прежде чем записать хоть один байт в **заранее подтверждённую** страницу.
   Программа копируется из проверенного ELF в отдельную BSS-страницу, не
   выполняется из файла PE, и остаток страницы обнуляется.
3. Узкий `--test-native-tea` на x86-64 заново использует T-P1.7 CPL3,
   SAFE/B user roots, TSS/IDT, аппаратный `int 0x80` и fault containment.
   Ранее статическая кодовая страница B заменена физически отличной BSS-страницей
   загруженного ELF с user RX; SAFE не отображает код пользователя,
   другая программа A имеет собственное физическое кодовое отображение.
4. PID B выдаётся реестром `process_runtime` и меняет состояние через
   `process_scheduler` на реальных trap событиях. Бинарник B выполняет
   YIELD, сохраняет регистры и данные через переключение, затем EXIT;
   A сначала YIELD, затем испытывает ожидаемый изолированный page fault.
5. Новый QEMU/OVMF runner запускает *настоящий* отдельный тестовый EFI,
   сверяет исходный `.tea` и SHA, аппаратные PC с символами ELF и
   вывод таблиц страниц с физической BSS-страницей, работу обоих PID,
   trap sequence, пользовательское состояние и возврат в SAFE. Неудачные
   состояния/таймаут/отсутствие QEMU не превращаются в PASS.

## Что не утверждается

- `.tea` пакет **читается/проверяется на этапе host-сборки**, а не из файловой
  системы гостя; ядро получает встроенные байты **ELF**, а не ZIP. В системе
  пока нет guest package parser, подписи/доверия к издателю, системной
  загрузки произвольного `.tea`, `dlopen`, динамической линковки, PLT/TLS/ASLR.
- Это специальный x86-64 тестовый профиль; он не запущен в нормальном
  Desktop и не привязан к `native_launch_stage` 767, UI-сеансу или окну.
  Отдельная пользовательская программа не является полноценным установленным
  приложением в интерфейсе.
- Корни тестового профиля отображают весь PE образ с историческим набором
  прав супервизора. Это **не** проверка production W^X для всего ядра,
  и не разрешение включать пользовательский root 762 в Desktop.
- Нет системного ABI для произвольных user-пойнтеров, копирующих syscalls,
  таймерной преэмпции, ресурсоизмерения CPU/RAM, IPC или общих файловых ACL.
- Контроль SHA-256 доказывает целостность **тестовых** байтов, не подлинность
  автора приложения; полноценный trust policy — отдельная архитектурная задача.
- Не затронуты `main`, прежние ветки, диск данных, текущие F5/F8/F10,
  интерфейс рабочего стола или каталог системных `.tea`.

## Команды

```sh
python3 tools/test_native_tea_768_host.py --output build/native-tea-host
python3 tools/build.py --arch x86_64 --test-native-tea --output build/native-tea-768
python3 tools/test_native_tea_768_guest.py --output build/native-tea-qemu
```

Последняя требует x86-64 QEMU + OVMF. Результат аппаратного теста считается
подтверждённым только по CI на точном финальном коммите.

## Следующий шаг 769

Сначала гостевой загрузчик **из реального файла** `.tea` на диске, с
верификацией в госте и изолированным ELF memory mapping. Затем объединить
загрузка → CPU/страницы → `native_launch_stage` → настоящий PID → сеанс → окно;
создать системный IPC для `Processes.tea`. Подключение утверждённого макета
экрана входа только после реальных пользовательских account/ACL и сеансов.
