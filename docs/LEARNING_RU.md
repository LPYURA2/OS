# Учебная карта StyleOS T-P1.7

## Какой путь проходит CPU

В Portable OS собственный CPU M32 исполнялся Python-моделью. В StyleOS компилятор создаёт команды настоящих ISA **x86-64** и **AArch64**. QEMU в тесте эмулирует выбранную аппаратную платформу, но внутри неё исполняется машинный код StyleOS. Python используется для подготовки файлов и запуска проверок, а не как ядро или пользовательская оболочка.

На x86-64 путь начинается в firmware UEFI. Оно находит `EFI/BOOT/BOOTX64.EFI` на FAT-разделе, загружает PE/COFF-образ и вызывает его entry. Наш адаптер получает карту памяти, завершает Boot Services, меняет стек на собственный, устанавливает собственную IDT и вызывает общее C-ядро. После этой границы UEFI console уже не является допустимым способом печати; используется COM1.

На AArch64 QEMU `virt` размещает raw Image и передаёт адрес DTB в `x0`. Начальный ASM сохраняет метаданные, приводит поддерживаемый EL2/EL1 старт к оговорённому EL1, готовит стек и C-окружение, запускает ранний UART и устанавливает собственные EL1-векторы. Платформенный UART PL011 позволяет напечатать тот же итог общего ядра.

## Как читать новую карту

`boot/x86_64/memory_map.c` отбирает обычную RAM из дескрипторов UEFI. `boot/aarch64/fdt_memory.c` достаёт RAM и резервы из DTB. `kernel/boot_memory.c` переводит оба варианта в одинаковые интервалы и вычитает из RAM резервы. `kernel/boot_memory_diagnostic.c` выводит итог только после полного успеха.

На ARM с 128 МиБ в Linux-прогоне UART показывает RAM `[0x40000000, 0x48000000)`. Образ начинается в `0x40080000`, поэтому кандидат ниже образа заканчивается ровно по этому адресу. Конец диапазона не включён. Первая страница внутри образа не попадает в кандидаты. Попробуйте найти такое же разбиение вокруг DTB и сравнить его положение при 256 МиБ.

`HANDOFF PASS` говорит о передаче управления, а `MEMMAP PASS` — о построении диагностической карты. Не путайте их: отрицательный тест карты проходит через успешный handoff и останавливается на `MEMMAP ERROR`.

## Термины на этом прототипе

**ISA** — машинные команды процессора. `x86-64` и `AArch64` требуют разных бинарников, даже если исходник C один.

**ABI** — договор о размещении аргументов, стеке, регистрах и двоичных структурах. На x86 UEFI используется Microsoft x64 calling convention; при переходе в общую C-часть нужно соблюсти именно ABI её сборки. Наличие одинаковой сигнатуры C само по себе не делает две несовместимые сборки взаимозаменяемыми.

**Стек** — память, которой функции пользуются для вызовов и локального состояния. Собственный стек после firmware boundary важен до появления любого аллокатора.

**Физический адрес** — адрес в аппаратном пространстве машины. Поле `uint64_t` с адресом не доказывает, что память по нему существует или доступна: стартовый код и будущий менеджер памяти должны обеспечить контракт.

**DTB** — бинарное дерево устройств, которое описывает платформу ARM. Текущий поддерживаемый парсер читает RAM и резервы для диагностики; автоматический поиск всех устройств и полноценная драйверная модель из этого не следуют.

**HAL** — аппаратный шов. Здесь он охватывает только раннюю serial-консоль и halt. Менеджер памяти, IRQ и драйверные службы из этого автоматически не следуют.

**PASS** — результат конкретной команды в конкретной среде. Host unit PASS проверяет C-логику; QEMU boot PASS проверяет путь CPU в выбранной модели; ни один из них не заменяет испытание физического устройства.

## Практика без изменения архитектуры

1. Откройте `boot_info.h`, найдите `size` и сравните с `_Static_assert(sizeof(struct boot_info) == 96)`. Посчитайте расположение `dtb` и найдите проверку смещения 56.
2. Прочтите `boot_info_validate()`: проследите, что произойдёт при неверной `version` или неизвестном флаге. Найдите соответствующий host-тест.
3. Сравните ранние UART-адаптеры: x86 пишет через порты, ARM — через MMIO. Найдите, почему общему `kernel_main()` эти регистры знать не требуется.
4. После запуска документированного smoke-теста найдите в serial-журнале entry архитектуры, вход `kernel_main`, валидацию handoff и halt. Запишите, какой вывод проверяет только старт, а какие системные возможности ещё отсутствуют.

Будущее безопасное упражнение в отдельной ветке — изменить только диагностическую строку, пересобрать обе архитектуры и подтвердить её в двух serial-журналах. Не меняйте для упражнения ISA, адрес загрузки, раскладку `boot_info` или правила UEFI ExitBootServices. Сохранённый коммит и отдельная ветка позволяют сравнить и отменить учебное изменение.

## Как читать собственную exception-диагностику

В обычном образе нет намеренного сбоя. `--test-exception` создаёт отдельный вариант: уже после установки обработчиков, валидного handoff и `MEMMAP PASS` выполняется конкретная ошибочная инструкция. Такой эксперимент позволяет проверить путь CPU → свой обработчик → UART, не выдавая обычный timeout за успешную диагностику.

x86-пример из подтверждённой сборки:

```text
STYLEOS EXCEPTION arch=x86_64 kind=sync vector=6 reason=invalid-opcode pc=0x000000000602db42 error=absent cr2=absent
STYLEOS EMERGENCY HALT
```

Vector 6 означает `#UD`: CPU встретил `UD2`. Сохранённый RIP указывает на эту инструкцию, а не на место печати строки. У `#UD` нет аппаратного error code: ноль, добавленный ASM для удобного кадра, не превращается в диагностические данные. CR2 относится к `#PF`, поэтому здесь он отсутствует и даже не читается.

Для проверки RIP недостаточно взять preferred base из PE-файла. Firmware загрузила эту сборку по `0x6029000`; `fault-site.json` указывает RVA `0x4b42`. Их сумма `0x602db42` должна совпасть с saved RIP и runtime-адресом trigger. Сами байты по доказанному месту в PE — `0f0b`.

ARM-пример из BRK-сборки:

```text
STYLEOS EXCEPTION arch=aarch64 kind=sync class=0x3c reason=brk pc=0x0000000040083908 esr=0x00000000f2000120 elr=0x0000000040083908 spsr=0x00000000600003c5 far=absent
STYLEOS EMERGENCY HALT
```

ESR описывает класс и детали исключения, ELR — сохранённый адрес инструкции, SPSR — состояние до входа. EC `0x3c` соответствует BRK; `0x120` — выбранный test immediate. FAR не является адресом инструкции: у BRK достоверного адреса ошибочного обращения нет, поэтому он `absent`. Нельзя печатать оставшееся значение FAR от другой ситуации как причину новой ошибки.

Исторический ESR `0x96000061` из T-P1.1 содержит Data Abort с alignment fault. T-P1.2 умеет распознать его в host-декодере. Этот числовой тест помогает понять причину старого сбоя, но не доказывает новый реальный Data Abort или восстановление из него. В T-P1.2 реальные управляемые ошибки — x86 UD2 и ARM BRK при начальных EL1 и EL2 → EL1. T-P1.4 добавляет отдельный опыт с отказом трансляции; его результат подтверждается только новыми журналами.

### Почему остановка отдельная

`STYLEOS KERNEL HALT` завершает обычный диагностический boot. `STYLEOS EMERGENCY HALT` означает терминальный exception-путь. Test runner требует правильный маркер и отвергает оба варианта, если они смешались. После ошибки нет возврата к инструкции, IRET или восстановления рабочего состояния.

Guard отмечает первый вход **до** форматирования. Повторная ошибка не печатает ещё одну полную запись и не пробует UART снова, а сразу останавливается. Если UART или стек сломан, даже первая запись может не появиться или оборваться; ограниченный polling защищает от бесконечного ожидания UART, но не гарантирует видимый вывод. Async ARM-входы не читают stale ESR; их поля помечаются отсутствующими. На x86 нет IST/аварийного стека и сохраняется зависимость от активной firmware GDT.

### Учебная практика T-P1.2 без изменения кода

1. Сравните `build/exception/*/fault-site.json` с exception-UART после отдельной сборки. Найдите сам opcode и объясните различие между file offset, RVA и saved PC.
2. Прочтите начало синхронного ARM-вектора: где берутся ESR, ELR и SPSR, какие действия происходят до первого вызова C? Сравните с unsupported IRQ/FIQ/SError-слотом.
3. Найдите `has_error` в x86 ASM и объясните, почему `#UD` печатает `absent`, а код `#PF` имеет аппаратное происхождение. Найдите условие чтения CR2.
4. Сопоставьте один normal-log и exception-log. Проверьте handoff и карту до fault, одну полную exception-запись, отдельный emergency halt и отсутствие обычного halt.
5. Сравните host-test saved ESR с реальным UART BRK. Объясните, какое утверждение подтверждает каждый из этих двух опытов.

Команда полного прогона и отдельного ARM64-only маршрута — в [TESTING](TESTING.md). Диагностика T-P1.2 прошла отдельные Linux- и телефонные прогоны; [телефонный отчёт](test-results/t-p1-2/termux/README.md) содержит 16/16 этапов. Это история базы. Отдельный [прогон T-P1.3 на Android](test-results/t-p1-3/termux/README.md) имеет 20/20 PASS. Owner-reported телефонные результаты предыдущих этапов учитываются отдельно и не заменяют новый прогон T-P1.7.

## Как читать первый пул страниц

У ядра уже есть память под собственный загруженный образ. Новый пул делит **один заранее выделенный массив** на восемь одинаковых частей. Ему не нужно искать свободную RAM и решать, кто владеет памятью firmware. Отдельный bitmap отмечает, какие из восьми частей выданы. Это позволяет изучить выдачу и возврат, пока право использовать общую RAM ещё не определено.

Начните с `boot_pool_check_layout()`. Диапазон `[base, base + bytes)` проверяется целиком, а сложение выполняется с защитой от переполнения. Если начало массива внутри образа, но конец вышел за его пределы, доступ запрещён. Конец диапазона не включён: `pool.end` — уже недопустимый адрес страницы. Выравнивание начала не заменяет проверку конца.

Свидетельство диагностики задаёт живой образ, стек, handoff, source и всю рабочую область карты. Проверка требует зарезервировать полный образ и исключает пересечения пула/его метаданных с этими областями. `boot_pool_admit()` сохраняет готовность только после успеха. При отказе страницы не читаются и не записываются подсистемой пула. Первоначальная очистка BSS загрузчиком — более ранняя часть настройки C-среды.

Далее проследите `boot_pool_alloc()`: он находит свободный бит, обнуляет все 4096 байт соответствующей страницы, помечает её занятой и возвращает адрес с явным `BP_OK`. Девятый запрос не находит места и возвращает null с `BP_EXHAUSTED`. В `boot_pool_free()` сначала проверяется адрес, затем bitmap; ошибочное освобождение не снимает занятость чужой страницы.

Обнуление при выдаче важно и при повторном использовании. Если вернуть страницу с ненулевым шаблоном и сразу запросить её снова, новый получатель должен увидеть нули. Но старый указатель продолжает содержать то же число: пул не способен отличить его от нового указателя на повторно выданную страницу. Поэтому use-after-free остаётся ошибкой вызывающего кода. Для нескольких CPU потребовались бы отдельные решения о синхронизации.

### Почему это ещё не PMM

Общий физический менеджер страниц должен доказать, какие области RAM можно передавать новым владельцам, где находятся действующие таблицы трансляции и другие структуры, какое отображение доступно ядру и когда можно вернуть загрузочную память. Текущий пул отвечает на более узкий вопрос: можно ли безопасно делить **известный массив внутри образа**, не повреждая соседние живые объекты?

Возвращаемый C-адрес описывает отображённую память этого массива. На ARM поддерживаемый Image выполняется по фиксированному адресу с MMU off. На x86 firmware уже отобразила PE; сравнение строится через реальный Loaded Image base и RVA. Это не универсальная функция перевода C-указателя в физический адрес. `MEMMAP CANDIDATE` по-прежнему не читается и не передаётся пулом для записи.

### Как проверить результат по журналу

1. Найдите `MEMMAP IMAGE`, `STACK`, `HANDOFF`, `SOURCE` и `RESERVED`. После `MEMMAP PASS` специальный образ должен вывести `BOOTPOOL RANGE`, `META` и `WORKSPACE`.
2. Посчитайте длину RANGE: конец минус начало должен дать 32768. Проверьте оба конца на делимость на 4096 и отсутствие пересечений с исключёнными областями. META имеет отдельные 4096 байт.
3. Сравните `pool-site.json` с UART. Для ARM это ELF/BSS/Image; для PE к обоим RVA прибавляется фактический runtime IMAGE start. Preferred ImageBase может быть другим.
4. Проверьте восемь записей ALLOC: индексы 0–7, разные выровненные адреса, ни одна страница не выходит из RANGE. Затем должны идти RW, EXHAUSTED, REUSE, PASS и обычный KERNEL HALT.
5. Сопоставьте адрес REUSE со страницей №3. Проверьте тестовый исходник: он читает все байты нулей, а не только сравнивает адрес, и убеждается, что остальные страницы не испорчены.
6. Откройте `tests/test_pool_output.py`: найдите примеры, где строка PASS есть, но неверные границы или отсутствующий шаг всё равно дают отказ. Сравните с lifecycle-проверкой QEMU, которая отвергает аварийный exit после маркера.

Не подменяйте фактический результат ожиданием. Для T-P1.3 сохранены собственные [журналы](test-results/t-p1-3/README.md) и отдельный телефонный отчёт; Linux ARM-only сам по себе не подтверждает прогон Android/Termux. Команда с закреплённым SHA и новой папкой — в [README](../README.md) и [TESTING](TESTING.md).

## От пула к собственному корню таблиц

Пул отвечает на вопрос «какая из восьми моих страниц сейчас занята?». Таблицы отвечают на другой вопрос: «какая физическая страница стоит за данным виртуальным адресом и с какими правами?». Свободный бит пула не создаёт mapping, а новая запись PTE не даёт права присвоить чужую RAM.

T-P1.4 использует отдельный известный резерв из 32 страниц внутри образа. Так не приходится расходовать восемь страниц пула или расширять mappings до всей RAM ради экономии таблиц. Сначала `pg_admit_layout()` проверяет **все** table/control/data границы и других владельцев. Потом `pg_build()` строит четыре уровня из 4-КиБ страниц. При ошибке его результат содержит `root=0`: частично записанные собственные таблицы не являются разрешением активировать их.

Изучайте `struct pg_mapping`: `va`, `pa`, `bytes` и `flags` имеют разный смысл. Адрес C-массива таблиц нужен ядру для записи дескрипторов; `tables_pa` нужен аппаратному walker. На ARM их соответствие выводится из проверенного фиксированного Image с MMU off. На x86 оно проверяется по унаследованным mappings; адрес GDT отдельно переводится старым walker, а не объявляется физическим по числу указателя. Её Accessed-бит может обновить CPU при загрузке CS: если A=0, только содержащая этот байт страница получает RW/NX после проверки полного PA-резерва вне кандидатов. При A=1 GDT остаётся RO/NX. Ядро не исправляет дескриптор программной записью и не создаёт новую GDT.

Следующий слой — `arch_paging_prepare()`: общий план не знает, что такое CR3, GDTR, TCR или PL011. Adapter проверяет допустимый режим и добавляет только критические платформенные страницы. `arch_paging_activate()` повторно проверяет условия и только затем меняет аппаратный корень. После этого код читает регистры обратно и снова обходит реальные дескрипторы каждой страницы.

У этого опыта честная простая политика: всё замыкание образа остаётся supervisor RWX. Это сохраняет код, стек, таблицы, exception path и страницы, которыми делятся разные секции. Нет W^X: NX у отдельного data-алиаса не отменяет execute в исходном image mapping. Промышленное разделение code/data — другая задача, требующая доказательства по страницам и времени жизни.

### Зачем нужен алиас

VA `0x0000400000000000` указывает на ту же data page, что исходный адрес внутри образа. Под новой схемой чтение через него должно увидеть `0x123456789abcdef0`; запись нового значения должна быть видна по исходному адресу. Такой опыт проверяет действие трансляции на данных, а не только число, прочитанное из CR3 или TTBR0.

Соседний VA `0x0000400000001000` намеренно не имеет leaf. Он канонический и входит в выбранный VA-диапазон, поэтому чтение должно дать **отказ трансляции**, а не ошибку размера/каноничности адреса. В fault-сборке `mov rax,[rcx]` на x86 вызывает #PF, а `ldr x1,[x0]` на ARM — Data Abort текущего EL. Исполняемая инструкция не заменяется программной печатью ошибки.

У #PF CR2 содержит адрес обращения, а saved RIP — адрес инструкции; они должны различаться по назначению. Error 0 означает supervisor read non-present без reserved-bit нарушения. В ARM FAR содержит адрес обращения, ELR — адрес LDR, а ESR должен показать EC 0x25, translation DFSC, чтение и валидный FAR. Runner проверяет все эти поля и executable opcode; для PE прибавляет фактическую runtime base к RVA.

### Как читать новые журналы

1. Найдите прежние HANDOFF/MEMMAP PASS. Переключение до них не допускается.
2. Сопоставьте TABLES/CONTROL/DATA с `paging-site.json`, IMAGE/RESERVED и исключёнными областями. Размер таблиц — 131072 байта, а не восемь страниц boot pool.
3. Сравните BEFORE, MAP и ROOT. В x86 посмотрите реальные GDTR/CS/IDT и GDT PA; в ARM — отдельный device PL011. ROOT должен принадлежать собственному резерву.
4. В AFTER найдите фактический аппаратный корень и режим. Сверьте каждую PTE с MAP: адрес страницы, PA, тип и права. Права задаются на странице, а не по имени C-функции.
5. Проверьте ALIAS before/after. В positive-варианте далее идут PAGING PASS и обычный halt. В fault-варианте — READY, одна точная exception-запись и только emergency halt.
6. Откройте host UART-тесты: найдите журнал с PASS, который отвергается из-за неверной PTE, root или синдрома. Сравните со штатной остановкой QEMU harness: естественный exit/reset не становится PASS.

Полные команды и список журналов — [TESTING](TESTING.md), архитектурные основания — [ADR-0007](adr/0007-owned-translation-tables-experiment.md), фактические статусы — [отчёт T-P1.4](test-results/t-p1-4/README.md). Android/Termux имеет отдельный статус; Linux ARM-only не является телефонным результатом.

## От трансляции к плану защиты T-P1.5

Запись PTE связывает VA с PA и задаёт права CPU. Владение отвечает на другой вопрос: кто вправе использовать эту физическую память и когда её можно передать дальше? Смена CR3 не освобождает firmware, а выключенная MMU ARM не превращает всю описанную RAM в память ядра. Поэтому T-P1.5 работает в отдельном профиле на прежнем CR3 / MMU off и ничего не выделяет из CANDIDATE.

Начните с трёх статусов. `PROTECTED` запрещает будущую выдачу страницы по известной причине: например, там живёт образ или действует базовый резерв UEFI/FDT. Это не права mapping. `REVIEW` означает только диагностический кандидат с `reason=no-transfer`: его ещё нельзя читать пробой, писать или выдавать. `UNCLASSIFIED` означает отсутствие достаточного покрытия для положительного вывода. Во всех случаях число реально переданных страниц в этом этапе — **`granted=0`**.

### Как проследить происхождение диапазона

`boot_memory_evidence` даёт полный образ, стек, handoff, источник и workspace диагностики. `ownership_plan_run()` сначала проверяет всю новую workspace относительно этих объектов и pool/metadata, затем заполняет input. Поле `kind` объясняет объект, `proof` — источник соответствия, `va` и `pa` сохраняются отдельно. На ARM PA известного объекта Image получается из проверенного MMU-off VMA=LMA. Для PE нужен действительный Loaded Image base; preferred base из файла не является адресом загрузки.

Новый union занимает ровно 65536 байт в BSS с выравниванием 4096. В нём находятся metadata входа, результата и временных расчётов. C-функции используют существующий стек внутри образа. Ни один диапазон REVIEW не становится адресом пробного чтения, обнуления или записи. Boot pool в этом профиле есть, но не допущен; таблицы/control/data T-P1.4 вообще не собраны.

Прочтите `op_build()`. Оно проверяет карту на копии прежним нормализатором, требует полный набор обязательных claims, проверяет физическую ширину, размеры, переполнения, ограничения массивов и согласованность VA/PA. Затем baseline RESERVED и живые claims округляются наружу до 4 КиБ и объединяются. Кандидаты уже округлены внутрь диагностикой; из них вычитается вся защита. Это даёт REVIEW без повторного учёта вложенных объектов.

Например, резерв `[0x1800,0x2100)` защищает `[0x1000,0x3000)`: обе частично занятые страницы сохраняются. Если внутри того же образа лежат стек и workspace, сумма их размеров не прибавляется ещё раз к числу защищённых страниц образа. Причины сохраняются отдельными claims, счётчик относится к объединению.

### Неполнота и ошибка — разные результаты

x86 читает текущие CR3/GDTR/IDTR/CS. Перед каждым разрешённым чтением старой table page вся её PA-страница уже должна быть RESERVED и вне CANDIDATE; аналогично допускается GDT. Дети берутся из активных дескрипторов, а ограниченное identity-замыкание подтверждает доступ к посещённым таблицам. Физическое чтение всё равно опирается на узкий поддерживаемый UEFI/OVMF контракт, а не на общий перевод произвольного PA в указатель.

`WALK/STEP` показывает реальные пути GDT и identity посещённых table pages. Runner независимо воспроизводит эти пути; он не получает дамп всех старых mappings. Могут существовать другие таблицы и firmware-зависимости, поэтому на x86 обязательны `unresolved=3`. Это честная известная неполнота при структурно согласованном плане. Она запрещает положительный вывод о передаче каждой REVIEW-страницы.

На ARM `root=0` говорит, что в этой фазе stage-1 MMU выключена. Код не читает и не очищает TTBR0 ради этого нуля. VBAR подтверждает executable vectors; полный DTB и его резервы сохраняются, а PL011 классифицируется как MMIO, не RAM. Даже `unresolved=0` для узкого QEMU virt набора не завершает передачу владения.

Отсутствующий IMAGE proof или противоречивый PA — уже ошибка обязательного свидетельства. `--test-ownership-plan-invalid` меняет только proof в собственном input; реальные handoff/map не повреждаются. Ожидается `STYLEOS OWNERSHIP ERROR: required` без частичных claims, диапазонов или PASS. Это демонстрация отказа, а не неполный опубликованный план.

### Практика по реальным артефактам

1. Соберите `python3 tools/build.py --arch aarch64 --test-ownership-plan`. В `build/ownership/aarch64/ownership-site.json` найдите workspace, diagnostic, stack, pool/metadata и vectors; для каждого посчитайте `end-start`. Проследите полный BSS/Image tail, а не только допустимость начала.
2. Сопоставьте UART IMAGE/STACK/HANDOFF/SOURCE с claims. Для PE прибавьте фактический IMAGE start к обоим RVA из sidecar. Объясните, почему на ARM handoff может быть вложен в стек.
3. Сравните PROTECTED с объединением RESERVED и наружных границ claims. Найдите вложенный объект, который не увеличивает суммарный счётчик. Из CANDIDATE вычтите защиту и сверьте REVIEW.
4. В x86 журнале воспроизведите один GDT walk по STEP, начиная с реального root, и найдите claim каждой посещённой table page. Объясните, почему это не доказывает полноту всех старых таблиц. Не изменяйте и не разыменовывайте напечатанные PA для упражнения.
5. Сравните STATE и STATE AFTER. Второй фактически снят после расчёта до публикации плана: CR3/MMU/GDT не меняются. У x86 обычные арифметические flags могут отличаться, IF/DF обязаны сохранять допустимое состояние.
6. Сравните ARM positive EL1/EL2 и 128/256 МиБ. Источником RAM должен оставаться DTB. Проверьте нулевой grant, причину каждого REVIEW и отдельный invalid-отказ.
7. Откройте `test_ownership_output.py`: найдите ложный PASS, подменённый диапазон и ненулевой grant, которые отвергает parser. Сравните с JSON runner: он содержит proof/снимки и SHA конкретных артефактов и UART, а не только статус.

Владельцы, фазы и сроки жизни перечислены в [ADR-0008](adr/0008-physical-memory-ownership-plan.md); команды и сохраняемые файлы — [TESTING](TESTING.md); фактические количества — [отчёт T-P1.5](test-results/t-p1-5/README.md). База T-P1.4 имеет отдельные 37/37 Linux, 27/27 Linux ARM64-only и 101/101 Python; это не новый Android PASS. Владелец сообщил в задании T-P1.6 о T-P1.5 Termux: 35/35, exit 0, QEMU 11.1.3 по скриншоту, без приложенных UART/JSON. Новый [отчёт T-P1.6](test-results/t-p1-6/README.md) фиксирует это отдельным owner-reported дополнением; исторический отчёт не переписывается.

## От плана памяти к двум задачам T-P1.6

Две доверенные функции могут использовать память, уже принадлежащую загруженному образу. Для этого опыта не нужно выдавать общую RAM: в новом отдельном `--test-tasks` профиле заранее размещены два BSS-стека по 16384 байта и 4096-байтный control union с выравниванием 4096. Прежние стек ядра на 65536 байт, handoff, диагностическая workspace и pool/metadata остаются отдельными живыми объектами. Сначала проверяются полные границы и архитектурное размещение; потом разрешаются записи в новые объекты. GRANTED остаётся нулевым, boot pool не допускается, heap не появляется.

### Состояние и исполнение — два слоя

`kernel/tasks.c` хранит только учёт. `tasks_create()` переводит FREE в READY; `tasks_go()` выбирает READY по round robin и отмечает RUNNING. Явная уступка переводит RUNNING обратно в READY, завершение — в DONE. `current=-1` означает исполнение диспетчера. При отсутствии READY возвращается EMPTY без изменения control. DONE не выбирается; только отдельный release переводит его в FREE и очищает slot metadata/context. Это не освобождение RAM и не общий allocator.

Сам C-движок не пишет в стек и не вызывает entry. После выбора общий демонстрационный код входит в ASM dispatch wrapper, который напрямую вызывает настоящий переключатель. Он сохраняет продолжение и SP текущей стороны, загружает их для другой стороны и переходит к сохранённому PC. У диспетчера это доказанный `styleos_tasks_dispatch_resume` на прежнем kernel stack. В первой задаче сохранённый PC указывает на bootstrap. После yield он указывает на инструкцию **после** CALL/BL переключателя. Поэтому следующая выдача READY продолжает тот же вызов, а не запускает функцию сначала.

Представьте две открытые книги: положение закладки соответствует PC, а все заметки на страницах — локальному состоянию стека. Одной закладки недостаточно, если обе книги пишут заметки в одно место. У A и B разные стеки; C хранит в них разные volatile local cookies и после двух уступок проверяет исходные значения и адреса внутри своего полезного полуинтервала. Диспетчер сохраняет отдельный context, а его собственный cookie остаётся на прежнем стеке ядра.

### Как начинается и завершается задача

Оба стека имеют по 16 байт canary у нижней и верхней границы; usable top равен `end-16`. На x86 начальный SP равен `usable_top-40`, то есть `SP % 16 == 8`: 8 байт занимает synthetic return address на trap, следующие 32 байта — shadow space Microsoft x64 ABI. Сохранённый PC указывает на bootstrap, и ASM входит туда через JMP. При обычном CALL переключатель сохраняет `SP=RSP+8` и PC из return address: последующий JMP восстанавливает состояние как после RET. Red zone запрещена флагами сборки.

На ARM usable top кратен 16, начальный SP ставится на него. X30 получает адрес return trap, PC — bootstrap. Переключатель сохраняет X19–X30, SP и PC из LR; BL записывает адрес продолжения в X30, а возврат к сохранённому PC делается через BR. Обычный C-код восстанавливает собственные stack frames при продолжении.

Bootstrap вызывает доверенную entry-функцию. Её нормальный return попадает обратно в bootstrap, который отмечает DONE и вызывает невозвращающийся ASM finish для передачи диспетчеру. Finish сохраняет контролируемый exit-resume PC: случайный выбор DONE попадёт в явную ошибку, а не продолжит полезную работу. Synthetic return trap также обнаруживает неожиданный return самого bootstrap. Это диагностические барьеры от неправильного перехода, без восстановления после повреждения задачи.

### Что проверяют регистровые шаблоны

ABI обещает сохранять определённые регистры через вызов. На x86 это RBX/RBP/RDI/RSI/R12–R15, на ARM здесь X19–X30. Отдельный ASM probe сначала сохраняет исходные значения C-caller на стеке, затем заполняет проверяемые регистры разными образцами: `0x1122000000000000 + (index << 32) + tag`, где tags A `0x101/0x102` и B `0x201/0x202` различают две уступки каждой задачи. Он напрямую вызывает переключатель и при resume сравнивает реальные регистры **до** восстановления исходных caller values. Маски `0xff` и `0x7ff` означают успешную проверку восьми x86 или одиннадцати ARM X19–X29; ARM LR дополнительно связывается с resume PC. Это сильнее проверки только структуры C, в которой хранятся копии регистров.

Контекст имеет 112 байт: двенадцать 64-битных GPR полей, SP по смещению 96 и PC по смещению 104. У x86 используются первые восемь GPR, остальные обнуляются. Сами значения volatile registers и арифметических flags не обещано сохранять через вызов. RFLAGS/NZCV, FP/SIMD, unwind и TLS не входят в экспериментальную ABI.

Компилятор ограничен integer-only режимом. `llvm-objdump` дополнительно декодирует все доказанные исполняемые байты связанного профиля и отклоняет неподдержанный FP/SIMD и неполное покрытие. Для ARM 60 байт header data после первой branch не являются командами. Проверка flags плюс реальный decode объясняют, почему здесь можно обойтись без FP/SIMD context; они не превращают опыт в поддержку произвольной программы с XMM/NEON или float.

### Практика по полному журналу

1. Соберите `python3 tools/build.py --arch aarch64 --test-tasks`. В `build/tasks/aarch64/tasks-site.json` найдите stack_a/stack_b по 16384 и control 4096; сверьте полный BSS и raw Image extent. Для PE отдельно прибавьте фактический Loaded Image base к обоим RVA, не preferred base.
2. Найдите в UART допуск объектов и обе READY-задачи. Проследите ровно шесть GO и события `A:START → B:START → A:RESUME → B:RESUME → A:EXIT → B:EXIT`.
3. Для каждой уступки сопоставьте saved SP с собственным полезным стеком и saved PC с resume symbol в proof. Проверьте tag каждого регистрового образца, полную маску после resume и неизменный local cookie по тому же адресу.
4. Найдите return из entry, DONE и возврат диспетчеру. После обеих DONE нужны EMPTY, release, целые canaries, совпадающие значимые STATE до/после, один `STYLEOS TASKS PASS` и обычный halt. Отдельный PASS без этого набора недействителен.
5. Сравните host-тест `tests/test_tasks.c` с настоящим QEMU job. Первый проверяет переходы и byte-identical отказ. Второй проверяет machine SP/PC и регистры; Python валидирует свидетельства, но не исполняет задачи вместо CPU.

Условия x86 inherited CR3/GDT/IDT и ARM EL1 MMU off сохраняются; observer только читает допустимые image/table/GDT объекты. Начальный ARM EL2 также проходит прежний переход в EL1. Нет смены address space, IRQ, таймера или вытеснения. Полные ABI-предпосылки — [ADR-0009](adr/0009-cooperative-kernel-tasks.md); команды, LLVM dependency и новый Termux-каталог с закреплённым SHA — [TESTING](TESTING.md); реальные количества и UART/JSON — [отчёт T-P1.6](test-results/t-p1-6/README.md).

## Граница результата T-P1.6

План подтверждает заявленную защиту и явные зависимости, а `granted=0` сохраняет нулевую передачу. T-P1.6 добавляет настоящую смену стека, продолжения и integer-состояния двух доверенных kernel tasks. Обе работают с теми же привилегиями и адресным пространством ядра: ошибка указателя одной может повредить другую или диспетчер. Software canaries только обнаруживают проверяемые изменения у концов стеков; они не останавливают запись за границы и не создают изоляцию.

Firmware/DTB/старые таблицы не освобождены, `MEMMAP CANDIDATE` не стал собственностью ядра, общий PMM/heap не появился. Нет recovery, IRQ, SMP, пользовательских процессов, syscalls, IPC или выбора микроядерной/гибридной модели. Deep Drop не реализован. Проверка того, что сбой пользовательского процесса не роняет ядро и вторую программу, из этого кооперативного опыта не следует. Отдельный профиль T-P1.7 вводит аппаратный пользовательский режим и границы доступа; его доказательства рассматриваются отдельно ниже.

Публикуется только `feature/styleos-t-p1-6` от `ea37e76abb0a1b6e75c050c43e357d8c89981537`, без обновления main, прежних refs, Portable-os, `docs/styleos-readme`, merge, force push или релиза. После отчёта работа останавливается. Первый пул из общей RAM, reclaim, собственная GDT и модель ядра требуют отдельных решений владельца.

## От доверенных задач к пользовательским программам T-P1.7

Привилегия отвечает на вопрос, **какие действия разрешены CPU**, а адресное пространство — **какая физическая страница стоит за данным VA**. В T-P1.6 обе функции были частью ядра. В T-P1.7 встроенные программы исполняются в CPL3 на x86 или EL0 на ARM. Их собственные таблицы не разрешают обращаться к kernel-only страницам; ошибка A должна остановить только её слот.

Начните с [ADR-0010](adr/0010-user-process-fault-isolation.md), затем проследите файлы по цепочке:

| Файл | Что связывает в сценарии |
|---|---|
| `include/styleos/user_processes.h` | Два слота, три roots, фиксированные VA, полный integer context и различие user frame/dispatcher |
| `kernel/user_processes.c` | READY/RUNNING/FAULTED/EXITED, допустимый порядок переходов и отказ без частичной мутации |
| `kernel/user_processes_demo.c` | Допуск статических ресурсов, A yield → B yield → A fault → B exit, снимки данных и окончательная проверка ядра |
| `arch/x86_64/user_processes.c`, `user_processes_entry.S` | C проверяет память и создаёт GDT/TSS/IDT; ASM выполняет IRETQ, захватывает INT/#PF и возвращается под SAFE CR3 |
| `arch/aarch64/user_processes.c`, `user_processes_entry.S` | C строит и проверяет MMU/TTBR0; ASM выполняет ERET, сохраняет EL0 SVC/Data Abort на SP_EL1 и возвращает диспетчер |
| `tools/user_processes_site.py` | Полные binary extents, отдельные code pages, точные инструкции/PC и связь с конечным образом |
| `tools/test.py`, `tests/test_user_processes*` | Настоящие QEMU jobs, строгий UART/JSON parser и отрицательные проверки ложного успеха |

### Один VA может обозначать разные страницы

У обеих программ код начинается с VA `0x10000000`, но root A ведёт к физической странице code A, а root B — к code B. Корни различны, а не являются двумя именами одного контекста. Стек A расположен в `0x11000000–0x11001000`, стек B — в `0x11010000–0x11011000`; data A — `0x12000000`, data B — `0x12010000`.

Под root A нет пользовательского отображения приватной страницы B. Под root B она есть и writable. Поэтому одно и то же обращение к `0x12010000` имеет разный смысл в двух контекстах. Код отображён user read/execute без write, данные и стек — user read/write без execute. Известные image aliases доступны только ядру: они не дают программе обхода user permissions. Полное ядро в этом эксперименте может сохранять supervisor RWX; это не общий W^X для StyleOS.

До первого запуска программа сборки доказывает **полный** размер объектов по конечному PE/ELF/Image, а runtime проверяет резерв и отсутствие пересечений. Три конечных резерва таблиц, пользовательские страницы и привилегированный стек уже принадлежат образу. Новая таблица меняет доступ к ним, а не делает `MEMMAP CANDIDATE` собственностью ядра. Нет общего аллокатора и выдачи RAM.

### Почему аппаратный вход не похож на обычный вызов функции

При C-вызове вызывающая сторона знает ABI и может считать volatile registers уничтоженными. Пользовательская программа исполняется отдельно, и исключение может наблюдать любое целочисленное состояние. Поэтому T-P1.7 сохраняет все 15 x86 GPR либо X0–X30 ARM вместе с пользовательскими PC/SP/status, а не только nonvolatile набор T-P1.6.

На x86 CPU видит CPL3 в CS. `INT 0x80` либо настоящий `#PF` меняет привилегию, получает RSP0 из TSS и строит hardware frame с RIP/CS/RFLAGS/RSP/SS. Пользовательский RSP не выбирает стек C-обработчика. На ARM SVC/Data Abort из EL0 приходит в lower-AArch64 synchronous vector; CPU сохраняет ELR/SPSR, а обработчик сохраняет GPR и SP_EL0 на привилегированном SP_EL1. Простая строка ядра «вошли в user mode» ничего из этого не доказывает.

Тестовый вход разрешает только yield и exit. Пользователь не передаёт указатель для произвольного чтения ядром. Обработчик проверяет текущий слот, реальный root, origin, operation и точный continuation PC. После входа активируется отдельный SAFE-root без user leaves, затем восстанавливается исходный dispatcher stack. Состояние аппаратного входа и контекст C-диспетчера хранятся отдельно.

### Как читать доказательство fault и продолжения B

В новом UART найдите A yield, затем B yield с сохранённым продолжением и данными `0x123456789abcdef0`. После этого A возобновляется и выполняет известную инструкцию чтения приватного VA B. На x86 нужны vector 14, CS RPL3, error `0x4`, CR2=`0x12010000` и точный RIP чтения. На ARM нужны lower-EL Data Abort EC `0x24`, сохранённый EL0t, read translation DFSC `0x7`, валидный FAR и точный ELR LDR.

PC user-инструкции — `0x10000000 + offset` внутри code A. Он не равен физическому адресу ASM-symbol в image. Найдите symbol/offset/opcode в `user-processes-site.json` и убедитесь, что runner связал его с SHA именно загруженного образа. Числа в логе не должны сравниваться с неподходящим preferred PE ImageBase.

После fault A становится FAULTED и больше не выбирается. В журнале должно быть **последующее** возобновление B на прежнем продолжении и стеке. B проверяет сохранённое значение, меняет его на `0xfedcba9876543210` и выполняет штатный exit через аппаратный вход. После возврата под SAFE-root ядро убирает терминальные контексты из учёта и выполняет финальную проверку. Только затем разрешены PASS и обычный halt. Страницы остаются в image reserve; release не является `free` общей RAM.

Чтобы увидеть разницу между аппаратным кадром и C ABI, найдите в программе B шаблон `0x55aa001122334455`: он записан в volatile R10 на x86 либо X9 на ARM до yield и сравнивается после возобновления. Обычный C-вызов мог бы уничтожить этот регистр, но пользовательский контекст должен его восстановить. B также проверяет значение на своём стеке и в приватной data page. В `FRAME`/`REG` записях доступны независимые снимки этого состояния, а `TABLE` записи позволяют runner заново обойти все три корня и проверить полный набор отображений.

Полезная учебная проверка — сопоставить четыре независимых источника: машинные инструкции программ, листья таблиц, hardware exception frame и строгий порядок UART. Ложный origin, другой VA/PC, fault B, выход B до fault A, повторный выбор A и журнал только с PASS должны быть отвергнуты отрицательными тестами. Успешный host-тест логики не заменяет три реальных запуска x86/ARM EL1/ARM EL2→EL1.
