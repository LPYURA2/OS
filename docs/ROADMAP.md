# StyleOS — дорожная карта

[Точка входа](PROJECT.md) · [Решения](DECISIONS.md) · [Идеи](IDEAS.md)

Даты и объём следующих работ уточняются по результатам испытаний. Ниже описаны результаты, а не обещание реализовать их одним патчем.

## Ближайшие настольные этапы

Владелец подтвердил тестовую сборку 703 в VirtualBox после обновления из
файла. Она становится опорной сборкой для своей основной ВМ. Публичный
выпуск и перенос GitHub-ветки `main` этим не утверждены. Старый VDI
не заменяем, следующие версии сначала проверяем в отдельной ВМ.

| Порядок | Этап | Критерий готовности |
|---|---|---|
| 1 | Управление и «Обновления» | Отдельная папка на диске данных. Один щелчок выбирает, двойной открывает, Enter остаётся. Клик по RU/EN и Alt+Shift меняют одну и ту же раскладку. |
| 2 | «Заметки» | По макету слева список и добавление, справа текст. Заметка сохраняется на диске и открывается после перезапуска. Текстовый редактор остаётся отдельным приложением для файлов. |
| 3 | «Документы» | Первый проход по макету приложения открывает реальный Word `.docx` из Проводника только для чтения. Сначала текст, заголовки и списки, затем сложная разметка и редактирование с сохранением. Старый бинарный `.doc` рассматривается отдельно. |
| 4 | Deep Drop между приложениями | Довести проверенный перенос текста в редактор и добавить приём в «Заметках» / «Документах» по мере появления получателей. Получатель видит только выбранный файл. Ошибка, Esc и отмена не трогают исходник, повтор не делает двойную вставку. |
| 5 | SDK и установка приложений | Подготовить обычную сборку внешнего приложения, пакет `.tea`, установку и запуск в госте. Первый сквозной результат — «Презентации» из `.tea` и редактируемый текст на слайде через Deep Drop. |

ISO остаётся допустимым образом для пробы и будущей установки. Возможность
оставить ISO первым носителем и подхватывать обновлённую сборку с диска
не входит в принятый тест VDI, это отдельная задача по удобству запуска.

## Первый инженерный выпуск

Владелец запускает StyleOS в VirtualBox, создаёт и сохраняет .txt, открывает его из «Файлов» после перезапуска, устанавливает самостоятельно собранные «Презентации» из .tea и через Deep Drop получает редактируемый текст на слайде. Это не публичная мобильная бета и не заявление о поддержке физического оборудования.

| Рубеж | Что должно получиться | Состояние |
|---|---|---|
| Загрузочный фундамент | Две архитектуры, контролируемая диагностика, независимые профили для памяти, задач и исключений. | T‑P1.0–T‑P1.7, [отчёты по этапам](BRANCHES.md). |
| Диск и внешняя программа | AArch64 гость сохраняет тестовый файл, затем загружает отдельно собранный файл из виртуального диска и запускает его в EL0. | T‑P1.8A и T‑P1.8B подтверждены, включая контроль владельца в Termux. Это не общая файловая система и не платформа .tea. |
| Экран x86‑64 | На диагностическом образе ядро рисует кадр после UEFI, обычный образ и ARM64 не меняются. | Linux/QEMU PASS и Termux PASS по COM1 для двух VDI. Диагностический образ и настольный профиль проверяются независимо. |
| Минимальный SDK и пакет | Внешний пример «Презентации» собирается обычным Clang, упаковывается в экспериментальный .tea, повреждённый пакет отвергается. | Инженерный этап для внешней установки. Хостовый пакет сам по себе не доказывает выполнение в StyleOS. |
| Первый рабочий образ | Рабочий стол с мышью и клавиатурой. Встроенные «Файлы», редактор и панель процессов. Сохранение, открытие через «Файлы» и повтор после перезапуска. | Десктоп и обновление подтверждены на 703. Подлинный список процессов пока не реализован — существующая панель показывает окна. |
| Установка из .tea | Собранные отдельно «Презентации» устанавливаются в действующей StyleOS без замены системного диска, запускаются и редактируют слайд. | Нужны рабочий образ и внешнее приложение x86‑64 в госте. Контейнер T‑P1.8B этого не обеспечивает. |
| Deep Drop и восстановление | Тот же .txt передаётся из «Файлов» в «Презентации». Отказ обработчика не приводит к падению оболочки или порче файла. | Перенос .txt в редактор проверен в QEMU. Получатель «Презентации» и изоляция сбойного обработчика остаются будущими критериями. |

### Приёмка первого рабочего образа

1. Создать .txt в редакторе на постоянном диске данных. Закрыть редактор, открыть этот же файл из «Файлов» и сравнить имя и содержимое.
2. Перезапустить VM, открыть сохранённый документ. Позже в том же контуре заменить только системный диск и повторить открытие. Прежний образ также должен читать совместимые данные.
3. Сверить панель с реальным учётом процессов. Она показывает системные и пользовательские процессы. Запуск и закрытие редактора меняют список. Диаграммы загрузки и принудительное завершение не обязательны для первого образа.

### Приёмка Deep Drop

Нормальный сценарий заканчивается редактируемым текстом на слайде. Получатель получает только выбранный файл, а не папку целиком. В аварийном сценарии после принятия файла и до вставки падает обработчик переноса. Незавершённую операцию отменяет система. Перезапускается только обработчик. Исходник, оболочка и приложения остаются доступны. Повтор вставляет текст один раз. Перезагрузка целой VM не считается восстановлением функции.

## Дальняя цель

- **Одна платформа** для десктопа и мобильного интерфейса. ПК и телефон с внешним монитором используют один десктоп; нативные порты и переключение режима проверяются отдельно.
- **Предсказуемое обслуживание.** Сначала установка системного обновления из файла с возвратом к рабочей версии. Затем один сетевой адаптер в VirtualBox и получение того же пакета из GitHub Releases. Интернет и браузер не нужны для первого образа.
- **Приложения и оформление.** Полноценные родные приложения, проверенные порты существующих программ, темы и «Офис» поверх работающей оболочки. В перспективе Android/Windows-совместимость как системные подсистемы, без обещания запуска любого APK или EXE.

## Утверждённый владельцем порядок дальнейшей разработки (24.11.2026)

1. Завершение фундамента системы: память, защитные механизмы, аппаратные зависимости, прерывания, изоляция и проверка безопасного перехода на собственные таблицы. Диагностические успехи не означают готовность production.
2. Файловая система: сохранность, восстановление, права доступа, совместимость данных при обновлении.
3. Независимые родные приложения .tea и их системные контракты.
4. Проводник.
5. Экран приветствия, входа, выбора пользователя и блокировки.

Интерфейс строго по утверждённым макетам (docs/design/APPROVED_UI_REFERENCES.md); существующий Desktop не изменять в фундаментальных этапах. Порядок выше заменяет прежнюю очередность, но не отменяет уже принятые результаты. Каждый новый этап в отдельной ветке, main и принятые refs неизменны.

Переход к файловой системе только после закрытия обязательных [критериев фундамента](architecture/FOUNDATION_COMPLETION_GATE.md) и отдельного сообщения владельцу о завершении.

Между реализацией фундамента и файловой системой обязательна [полная приёмка ядра](architecture/KERNEL_FINAL_ACCEPTANCE.md): интегрированный SHA, реальные аппаратные, защитные, нагрузочные и регрессионные проверки с независимым разбором доказательств. Решение владельца 24.11.2026.

После успешной комплексной приёмки ядра и до файловой системы — отдельное обсуждение владельцем [технического уровня, оптимизации, производительности и системных требований](architecture/POST_ACCEPTANCE_PERFORMANCE_REVIEW.md). Числа не утверждены; решение об объёме дальнейшей оптимизации принимает владелец.
