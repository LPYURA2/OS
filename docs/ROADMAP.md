# StyleOS — дорожная карта

[Точка входа](PROJECT.md) · [Решения](DECISIONS.md) · [Идеи](IDEAS.md)

Даты и объём следующих работ уточняются по результатам испытаний. Ниже описаны результаты, а не обещание реализовать их одним патчем.

## Первый инженерный выпуск

Владелец запускает StyleOS в VirtualBox, создаёт и сохраняет .txt, открывает его из «Файлов» после перезапуска, устанавливает самостоятельно собранные «Презентации» из .tea и через Deep Drop получает редактируемый текст на слайде. Это не публичная мобильная бета и не заявление о поддержке физического оборудования.

| Рубеж | Что должно получиться | Состояние |
|---|---|---|
| Загрузочный фундамент | Две архитектуры, контролируемая диагностика, независимые профили для памяти, задач и исключений. | T‑P1.0–T‑P1.7, [отчёты по этапам](BRANCHES.md). |
| Диск и внешняя программа | AArch64 гость сохраняет тестовый файл, затем загружает отдельно собранный файл из виртуального диска и запускает его в EL0. | T‑P1.8A и T‑P1.8B подтверждены, включая контроль владельца в Termux. Это не общая файловая система и не платформа .tea. |
| Экран x86‑64 | На диагностическом образе ядро рисует кадр после UEFI, обычный образ и ARM64 не меняются. | Linux/QEMU PASS и Termux PASS по COM1 для двух VDI. VirtualBox — отдельная ожидающая проверка. |
| Минимальный SDK и пакет | Внешний пример «Презентации» собирается обычным Clang, упаковывается в экспериментальный .tea, повреждённый пакет отвергается. | Ближайший узкий инженерный шаг. Сам по себе не доказывает выполнение в StyleOS. |
| Первый рабочий образ | Рабочий стол с мышью и клавиатурой. Встроенные «Файлы», редактор и панель процессов. Сохранение, открытие через «Файлы» и повтор после перезапуска. | Цель согласована. Графический диагностический экран её не закрывает. |
| Установка из .tea | Собранные отдельно «Презентации» устанавливаются в действующей StyleOS без замены системного диска, запускаются и редактируют слайд. | Нужны рабочий образ и внешнее приложение x86‑64 в госте. Контейнер T‑P1.8B этого не обеспечивает. |
| Deep Drop и восстановление | Тот же .txt передаётся из «Файлов» в «Презентации». Отказ обработчика не приводит к падению оболочки или порче файла. | Сначала перенос и восстановление можно проверить на хостовом стенде, затем отдельно в StyleOS. |

### Приёмка первого рабочего образа

1. Создать .txt в редакторе на постоянном диске данных. Закрыть редактор, открыть этот же файл из «Файлов» и сравнить имя и содержимое.
2. Перезапустить VM, открыть сохранённый документ. Позже в том же контуре заменить только системный диск и повторить открытие. Прежний образ также должен читать совместимые данные.
3. Сверить панель с реальным учётом процессов. Она показывает системные и пользовательские процессы. Запуск и закрытие редактора меняют список. Диаграммы загрузки и принудительное завершение не обязательны для первого образа.

### Приёмка Deep Drop

Нормальный сценарий заканчивается редактируемым текстом на слайде. Получатель получает только выбранный файл, а не папку целиком. В аварийном сценарии после принятия файла и до вставки падает обработчик переноса. Незавершённую операцию отменяет система. Перезапускается только обработчик. Исходник, оболочка и приложения остаются доступны. Повтор вставляет текст один раз. Перезагрузка целой VM не считается восстановлением функции.

## Дальняя цель

- **Одна платформа** для десктопа и мобильного интерфейса. ПК и телефон с внешним монитором используют один десктоп; нативные порты и переключение режима проверяются отдельно.
- **Предсказуемое обслуживание.** Сначала установка системного обновления из файла с возвратом к рабочей версии. Затем один сетевой адаптер в VirtualBox и получение того же пакета из GitHub Releases. Интернет и браузер не нужны для первого образа.
- **Приложения и оформление.** Полноценные родные приложения, проверенные порты существующих программ, темы и «Офис» поверх работающей оболочки. В перспективе Android/Windows-совместимость как системные подсистемы, без обещания запуска любого APK или EXE.
