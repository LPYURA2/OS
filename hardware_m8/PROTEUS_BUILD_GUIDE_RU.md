# MATRYOSHKA M8 — аппаратная ветка для Proteus

**Статус:** архитектура, ассемблер, ROM и программная пофазная модель протестированы. **Готовой `.pdsprj` / `.dsn` схемы Proteus в архиве нет**: проводники и микросхемы в Proteus ещё не соединены и логическая симуляция не проверена. Этот документ — протокол сборки и сверки с эталоном, не утверждение о готовом железе.

## Почему две ветки

- `../matryoshka.py`: **MATRYOSHKA-32**, 16 регистров, ядро и задачи на собственном ассемблере, 256 КиБ. Это гостевая ОС прототипа. Её машинный код **не совместим** с M8.
- `m8.py`: **M8**, новая 8-битная микроархитектура специально для сборки из цифровых логических элементов. 25 инструкций, ROM-монитор в `boot.m8asm`. **Не полноценная ОС**. Наш первый аппаратно реализуемый кандидат.
- Цель — затем договориться об общем формате файлов/ABI, написать компилятор либо портировать ядро на целевой ISA. Нельзя просто залить `kernel.asm` MATRYOSHKA-32 в M8 ROM.

## Тактирование и машинный код

В КАЖДОЙ инструкции **3 байта**, little-endian:

```
байт 0 = OP
байт 1 = IMM_LO
байт 2 = IMM_HI
```

Цикл исполнения из **4 фаз**:

| Фаза | Шина адреса | Что делаем |
|---|---|---|
| T0 | PC | IR <- ROM/RAM[PC]; PC++ |
| T1 | PC | IML <- ROM/RAM[PC]; PC++ |
| T2 | PC | IMH <- ROM/RAM[PC]; PC++ |
| T3 | зависит от OP | Исполнить IR, опционально использовать X для `LDA_X`/`STA_X`, ветвление меняет PC |

Инструкции `JMP`, `JZ`, `JNZ`, `LDXI` используют 16-битную константу `IMH:IML`. Остальные — младшие 8 бит (или игнорируют immediate). 16-битный PC увеличивается с переполнением на 0; X тоже. 8-битная ALU выставляет Z, а при `ADD/SUB/CMP` также C/borrow по правилам `m8.py`. `LDAI`, `LDBI`, `LDA_X`, `INCA`, `DECA`, `IN` также могут обновлять Z. 25 инструкций см. в `m8.py`.

## Адресное пространство / шина

```
A15 = 0 -> ROM 0x0000..0x7FFF (32 KiB, 27256/27C256)
A15 = 1 -> RAM 0x8000..0xFFFF (32 KiB, 62256)
общая 8-битная DATA0..7
```

**Правило для ROM:** запретить сигнал записи на ROM. Это в программной модели тоже защищено. При запуске PC=0x0000, на шине первые байты ROM (boot). В фазах T0-T2 читаем из PC, в T3 для операций косвенной памяти — адрес X. На шину данных в каждый момент может выводить данные только **одна** активная микросхема (контроль `OE/CE`, трёхсостояния).

## Модули для поэтапной сборки

| Блок | Логическая роль | Кандидаты микросхем для поиска в Proteus |
|---|---|---|
| Тактовый генератор | `CLK`, однократный шаг | Digital CLOCK, кнопка с подавлением дребезга |
| Счётчик фаз | T0/T1/T2/T3 | 74HC161 или триггеры, декодер 74HC139 |
| PC 16 bit | Инкремент и параллельная загрузка адреса | четыре 74HC161 (каскад + загрузка) |
| X 16 bit | Регистр адреса данных | два 74HC574, инкрементный тракт |
| IR/IML/IMH | Три 8-битных регистра | три 74HC273 / 74HC574 |
| ALU 8 bit | ADD, SUB, AND, OR, XOR, CMP | логические элементы + сумматоры или 74HC181 с доработкой |
| Регистр A и B | Данные CPU | два 74HC574 |
| Мультиплексор адреса | PC или X | четыре 74HC157 (по 4 бита) |
| Дешифратор управления | OP + T3 + флаги | 74HC138, 74HC00, 74HC08 и др. |
| ROM | Firmware, байты машинного кода | 27C256 или 27256 (32Kx8) |
| RAM | Чтение/запись | 62256 (32Kx8) |
| Порт OUT 0 | 8 бит данных наружу | 74HC273 + 8 светодиодов на первом тесте |
| Порт IN 1 | 8-битная «клавиатура» | DIP8 + strobe/ready + latch (или контроллер клавиатуры позднее) |

Это **кандидаты**, а не готовый перечень закупки: нужные реализации сигналов, совместимость напряжений и наличие моделей проверяются в конкретной версии Proteus. Для X+1 и X-1 потребуются дополнительные сумматоры/счётчики; простой 16-битный latch этого не умеет.

## Последовательность первой электрической проверки в Proteus

1. Поставить CLOCK, 2-битный счётчик фаз, вывести T0..T3 на индикаторы и осциллограф/logic analyzer.
2. Собрать 16-битный PC (инкремент на T0/T1/T2, загрузка только во время T3 у переходов). Проверить последовательность 0000,0001,0002,0003.
3. Подключить ROM 27C256 и загрузить `rom32k.hex` или `rom32k.bin` **в формате, поддерживаемом свойством выбранной ROM-модели**. Сверить первые байты с `boot.bin`.
4. Добавить IR/IML/IMH и сигналы latch. Проверить, что каждые четыре такта формируется одна инструкция с фиксированным адресом.
5. Собрать регистры A/B и Z, сначала только инструкции NOP, LDAI, CMPI, JZ, JMP, OUT, HALT.
6. Подключить 8 светодиодов к выходному регистру OUT0. На старте ROM печатает не ASCII на светодиодах, а **байтовые коды** — их можно наблюдать логическим анализатором. Для букв нужен внешний экранный интерфейс/контроллер.
7. Добавить 16-битный X, `LDA_X`/`STA_X`, RAM 62256, затем весь набор ALU. Сравнивать с `golden_trace.csv`.
8. Добавить IN1 (начать с ручного ввода ASCII по DIP-переключателям с ready). Для нормальной клавиатуры и дисплея дальше нужны отдельные драйверы или контроллеры.

**Важное ограничение экрана:** `OUT 0` в Python-модели сразу добавляет ASCII в текстовый вывод. В Proteus это лишь 8-битная шина и импульс `WR`. Подключить её напрямую к Virtual Terminal и получить буквы нельзя: нужен UART/serialiser либо LCD-контроллер с корректным протоколом записи. На первом аппаратном этапе это **байтовый порт, не готовая видеокарта**.

## Файлы

- `boot.m8asm` — ROM-монитор, написан на нашем ассемблере.
- `boot.bin` — программа (418 байт).
- `boot.hex` — Intel HEX для только используемых адресов.
- `rom32k.bin` и `rom32k.hex` — полные 32768 байт ROM с заполнением неиспользуемой области 0xFF.
- `m8.py` — ассемблер + эталон CPU со счётчиком фаз.
- `gate_alu.py` — модель сумматора из элементарных битовых вентилей и проверка 327 680 комбинаций ALU.
- `golden_trace.csv` — эталонные состояния CPU на каждую фазу первых инструкций; сверять с логическим анализатором Proteus.

## Первые действия в программе

Смоделированный ROM-монитор печатает заставку и `M8>`. Односимвольные команды:

- `h` — help;
- `m` — записать 0x5A в RAM[0x8000], прочитать и проверить;
- `p` — вывести конфигурацию;
- `q` — остановить CPU.

Это не ещё одна виртуальная ОС, а bare-metal загрузчик/монитор для проверки собственной схемы. Следующая цель — драйвер видеоконтроллера, файловая система и перенос гостевой ОС на аппаратно реализуемую ISA.

## Microchip Studio — что именно с ним делать

Он собирает код в AVR/SAM ISA, **не** в M8 ISA. Используем его только если отдельно добавим AVR/SAM сопроцессор для обслуживания дисплея/клавиатуры или выберем ветку с готовой MCU. В основной M8 ветке сборка прошивки: `python m8.py --build` и файлы ROM для Proteus. Для новых AVR/SAM проектов Microchip рекомендует MPLAB X / MPLAB for VS Code вместо Microchip Studio.

## Ограничения безопасности и реалистичности

- Это экспериментальный учебный процессор, не сертифицированный контроллер и не безопасная среда для недоверенного кода.
- Прошивка на реальном PCB, Proteus, FPGA и ASIC **ещё не проверена**. Никаких заявлений об изготовленном кристалле.
- При переходе к физическому железу нужна проверка таймингов, стабильности питания, уровня сигналов, удержания данных и конфликтов на шине.
