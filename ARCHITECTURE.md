# MATRYOSHKA v0.2 — описание архитектуры

## Software CPU MATRYOSHKA-32 (совместимо с v0.1)
- 33 пользовательские/привилегированные инструкции, 8-байтное кодирование, 16 32-битных регистров.
- Прошивка в ROM и ядро в RAM, обе программы собраны встроенным двухпроходным ассемблером.
- Планировщик процессов и обработчик системных вызовов исполняются как собственный гостевой ассемблер, а не как Python-планировщик.
- Виртуальная клавиатура через IN port 30 и системный вызов TRAP 8.
- Виртуальный 40x14 текстовый экран: Python-устройство, обновляемое при терминальном выводе и очищаемое через OUT port 40 из гостевого ядра (TRAP 9).
- Гостевой `shell.asm`: читает клавиши системным вызовом, собирает буфер и сравнивает байты команд на виртуальном CPU.
- Python `--os` предоставляет только транспорт строк в виртуальную клавиатуру и вывод консоли пользователю.
- Пока НЕТ полного VFS, событийной клавиатуры по сканкодам, графики, динамического загрузчика с виртуального диска, собственных драйверов видео на гостевом ассемблере.

## Hardware-targeted CPU M8
- НОВАЯ несовместимая ISA, 25 опкодов, 3 байта на инструкцию, 4 тактовые фазы T0..T3.
- PC/X 16 бит; A/B 8 бит; флаги Zero/Carry.
- 64 КиБ адресного пространства (32K ROM, 32K RAM), ROM monitor — 418 байт.
- Выходной параллельный 8-битный порт OUT 0; вход IN 1 — в Python модели FIFO символов.
- Модель `m8.py` пригодна как test oracle; `golden_trace.csv` — образец тактов для сопоставления с будущей схемой Proteus.
- `gate_alu.py` использует 1-битные логические вентили и полный перебор 327680 случаев пяти ALU операций, без симуляции задержек вентилей.
- `rom32k.hex` и `.bin` сгенерированы нашим ассемблером, но пока НЕ загружались в реальный Proteus.

## Технический долг / ограничение
- 32-bit и M8 имеют разные ISA, их программы НЕ совместимы. Для настоящего переноса нужна одна из стратегий: портирование ядра на M8; постепенное расширение M8 до M16/M32; синтезируемая копия MATRYOSHKA-32 ISA на FPGA.
- Ни одна из схем не является полноценным PC или готовым аналогом Windows/Linux. Это исследование собственного стека вычислительной машины.

## Добавлено в Termux v0.3.1: ROM → SYSTEM.IMG → ядро
- **Временная ISA:** прежняя M32, не согласованная для Proteus. Не считать выбранной архитектурой будущей ОС.
- Python копирует в ROM только `images/firmware.bin`. Область RAM по адресу 0x2000 перед началом исполнения пуста.
- ROM код на гостевом ASM читает заголовок SYSTEM.IMG (сектор 0) во временный буфер 0x7000. После проверки `MTRX`, byte length и sector count (1..16) загружает сектора 1..N по адресу 0x2000.
- ROM вычисляет простую сумму 32-битных слов и сравнивает её с полем заголовка, затем делает `JMP 0x2000`. Ошибка формата или контрольной суммы приводит к сообщению BOOT ERROR и HALT.
- Порты только чтения для системного диска: OUT 50 (номер сектора), OUT 51 (адрес назначения RAM), OUT 52 (команда 1=READ), IN 53 (1=OK, 0=ERROR). Устройство в Python переносит сектор в RAM, **но командует переносом гостевой код**.
- SYSTEM.IMG — неизменяемая для гостевой ОС копия 128×512 байт. Пользовательский диск с NOTE.TXT отдельный; прежний syscall BLOCK работает с ним.
- ВАЖНО: гостевые приложения ещё размещает Python из *.asm. ROM-загрузчик ядра подтверждён, но вся операционная система пока не является автономным дисковым образом.

## T1A / v0.3.2: гостевой загрузчик приложений

- Системный диск — 128 × 512 байт, чтение через аппаратные порты 50–53. Firmware читает ядро из секторов 1..N, как в v0.3.1.
- Сектор **17** — каталог `MAPP` v1: заголовок 16 байт (`magic/version/count/reserved`); затем до 8 записей по 40 байт: `name[16]`, `load_addr`, `start_sector`, `sector_count`, `byte_length`, `word_checksum`, `flags` (u32 little-endian).
- Секторы **18..127** — связанные на фиксированный адрес бинарники. Каталог создаётся **на хосте при сборке**, но считывается и разбирается **кодом ядра на M32 во время работы**.
- Привязка слотов: `APP_BASE=0x8000`, размер `0x3000`; индекс 0..5 соответствует `hello`, `counter`, `taskmgr`, `diskdemo`, `selfmod`, `shell`. Код собран для абсолютного адреса каждого слота. Образы системного и пользовательского дисков различны.
- Гостевой boot: читает `MAPP` в 0x7000, валидирует поля, по порту выбора запуска (IN 10/INIDX 11: аппаратный аналог boot profile) получает ID программы, читает сектора и проверяет сумму слов. Python **не копирует** код программ в RAM при `boot()`.
- Гостевой syscall `TRAP 10`: R0=ID, результат в R0=0/0xFFFFFFFF. Ядро проверяет PID/слот, при необходимости загружает приложение из системного диска и вызывает `SPAWN`. Слот нельзя перезаписывать, пока процесс жив. Данные таблицы `slot → PID` хранятся **в гостевой памяти ядра**.
- CPU Python обрабатывает `SPAWN` как привилегированный аппаратный механизм изменения состояния процессного контекста; сам выбор, чтение, проверка и контроль занятости находятся в гостевом ядре.
- Проверки образов используют **не криптографический** аддитивный checksum; это обнаружение многих случайных повреждений, но не гарантия подлинности или безопасности. ISA, бинарный каталог и TRAP 10 являются прототипами, без гарантий совместимости будущих выпусков.
- Известный долг: максимум 8 записей о PID за запуск, без освобождения идентификаторов; смешивание текстового вывода конкурирующих задач; отсутствует динамическая линковка/перемещаемый код и VFS.
